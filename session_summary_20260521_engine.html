The Session — How the Architecture Was Built

A Design Session That Went From Analogy to Architecture to Code

This is not a summary of decisions made in isolation. The architecture emerged from a structured dialogue — hypothesis, challenge, correction, lock. Below is the story of how the key design choices were reached, with links to where each decision lives in the documents.

Step 1 — Establishing the System Type

The first question was: what kind of system are we building? The wrong answer would have been "a document search" or "a lookup table." The correct framing came from the user's requirement: exact portal, exact left-nav item, exact tab, exact field label, exact dropdown value, exact button to click. Per step. Version-aware.

"Show me the workflow for AP VLAN tagging. Or tell me which menu to get to to configure the CWP for PPSK. Not just 'where do I start' — the exact screen, the exact tab, the exact field."

— User, establishing the precision requirement that drove the GPS navigator analogy

The analogy that locked: GPS navigator for UI configuration. XIQ is the starting map. EP1 is the destination. The engine knows every road, one-way street, and detour — including roads EP1 hasn't built yet. See Tab 1: System Design → GPS Analogy.

Step 2 — Query Classification

Two example queries from the user immediately revealed that different queries require different graph traversal strategies, not just different prompts. This led to the three-type query classifier — a decision that shapes every node in the graph.

TypeUser's ExampleGraph Strategy
workflow"Show me the workflow for AP VLAN tagging"Full Neo4j path traversal — multi-step, ordered, all screens
lookup"Which menu to configure CWP for PPSK?"Single Neo4j node — nav path only, short-circuit
compare"What's different between XIQ and EP1 for switch policy?"Dual subgraph diff — side-by-side table output

Both workflow and lookup return the same confidence scoring format. lookup short-circuits the full traversal. All three go through the same classifier first. See Tab 1: Query Classifier.

Step 3 — Three Layers of Truth

The design question was: how do you know if a mapping is correct? Documents say one thing. The live GUI may differ. And neither tells you whether the config works in a real lab. The answer: three independent signals, each with a weight, combined via Σ(w×c)/Σ(w) — the same formula used in the Cisco EN CLI Agent architecture.

LayerSourceWeightWhat It Tells You
L1 — RAG14 PDFs → pgvectorc_doc = 0.3What the documentation says should exist
L2 — GUI CapturePlaywright → Neo4jc_gui = 0.4What actually exists in the live EP1 UI right now
L3 — Live LabExecution Agent → PostgreSQLc_lab = 0.3What actually works when you push the config

When c_lab is absent (not yet lab-validated), the formula renormalises over c_doc + c_gui. This means the engine is useful from day one, with confidence that improves as lab data accumulates. See the confidence formula in the transition guide and Tab 1: Three Layers of Truth.

Step 4 — The RAG vs Scrape Matrix

For any given XIQ feature, the combination of RAG result and Playwright scrape result produces one of exactly four outcomes. This matrix is the core classification logic that drives confidence scoring and gap detection.

2Says X exists at path AFinds X at path BRestructuredMED 0.50–0.69
3Says X existsFinds nothingGap — log to registerGAP < 0.40

G-01, G-02, and G-03 from the KhKLab deploy (earlier today) are already outcome 3 — gaps. They are seeded into the engine's gap register on day one. See the Gap Register.

Step 6 — Can the Engine Learn? The Exchange That Changed the Architecture

The question was posed directly: can this architecture learn and grow? The initial answer described confirmed_examples in pgvector as the primary learning mechanism — curated mappings accumulate over time, feeding the LLM better context. The user probed this. What followed was the most important exchange of the session.

Verbatim Dialogue — 20:45 May 21, 2026 — The Architectural Correction
Khursheed Khan

"So, there is NO way for the Lead_AI_Agent to anticipate the next step without having in memory somethig similar? This seems to be counterintuitive to learning. Take googl_maps for example. It does not know how to go form a to b but just executes commands based on what is stored. So, we are looking for the metrics our agents will use to guide it from source to destination, sort of like guiding a blind person around the block with audibles? Even in google maps, I must double check the route and destinatoin :)"

Verbatim — original spelling preserved
Claude (Response)

You've identified a genuine architectural gap. Let me be precise about what I missed and what needs to change.

What I designed was reactive, not anticipatory.

The confirmed_examples store finds similar past trips. That's semantic memory. What Google Maps uses is fundamentally different: a weighted directed graph where the weights ARE the encoded learning. Maps doesn't retrieve "similar routes." It traverses a graph where every edge has metrics — distance, speed, traffic — and those metrics ARE the knowledge. The route is found by executing an algorithm over those weights, not by remembering analogies.

Our Lead Agent (Node 0) currently has no lookahead. It routes to Node 1, waits, routes to Node 2, waits, discovers a gap at step 4. That's a blindfolded walk. The audible guide model requires Node 0 to plan the full path FIRST, compute its confidence BEFORE moving, and announce what's coming.

The correction: two distinct types of encoded knowledge

TypeWhere it livesWhat it ISGoogle Maps equivalent
StructuralNeo4j edge propertiesThe navigation graph with weighted roadsRoad network + traffic data
Semanticpgvector (RAG + confirmed_examples)What concepts mean, how to explain stepsPOI names, address geocoding

The confirmed_examples store is semantic — it helps Node 4 explain a step. But the structural learning — "this road has been driven successfully 12 times, that road has a pothole" — must live as edge weights in Neo4j.

What every Neo4j edge needs — the "road quality" properties

XIQ_node -[MAPS_TO {
    confidence:        0.87,   ← current weight (the road quality)
    c_doc:             0.80,   ← what docs say about this road
    c_gui:             0.90,   ← what scraper found at this road
    c_lab:             0.85,   ← how many cars have driven it successfully
    traversal_count:   12,     ← total attempts
    success_count:     11,     ← successful traversals
    last_validated:    2026-05-21,
    source:            "lab",  ← highest-quality validation
    version_pair:      "XIQ-25.8.0__EP1-25.9.0"
}]-> EP1_node

Learning = updating these edge properties.
When the Execution Agent validates a step, it updates the Neo4j edge.
The graph IS the memory.

Node 0 gets path planning — the anticipatory capability

Before executing anything, Node 0 must:

1. Get full path (XIQ seed → EP1 destination) via Neo4j Cypher shortest-path
2. Read all edge properties on every hop
3. Compute:
   - path_confidence = min(edge.confidence) ← worst bottleneck
   - low_confidence_steps = edges where confidence < warn_threshold
   - gap_steps = edges where confidence < gap_threshold OR edge doesn't exist
4. Generate "route preview" BEFORE execution:
   "This workflow has 6 steps.
    Step 3 confidence: 0.42 (LOW) — EP1 nav path changed in 25.9.0, verify manually
    Step 5 confidence: 0.28 (GAP) — no EP1 equivalent found, workaround available
    Steps 1, 2, 4, 6 confidence: HIGH (>0.80), lab-validated 8+ times"
5. Surface HITL checkpoints upfront — user confirms before traversal begins

This is the audible guide. You are told about the curb before you reach it, not after you trip.

HITL repositioned — not just for correction, but for confirmation gates

You're right that agents cannot deliver 100% guarantee. HITL is the formal acknowledgment of that. But it operates at two levels:

  1. Upfront confirmation gate (Node 0's route preview) — "here are the low-confidence steps, do you want to proceed?"
  2. Mid-traversal pause (Node 6 → Gap Curator) — "I've hit a gap, here's my best guess, confirm before I continue"

Like Google Maps: you see the route summary before you drive (level 1), and if there's a complex interchange it says "keep right in 200m" to prepare you (level 2). You still verify the final destination.

Why "Guiding a Blind Person Around the Block with Audibles" Is the Better Framing

The Google Maps analogy captures the graph-traversal and edge-weight mechanics perfectly. But the user's audible guide framing adds something Maps doesn't: the engine must announce what's ahead so the user can prepare, not just compute the optimal route. A GPS for a sighted driver can show a map and let the driver figure it out. An audible guide for someone who can't see the obstacles must be proactive — "curb in 3 steps, low-confidence corner ahead, gap at the intersection." That is exactly what the route_preview + two-level HITL design achieves. The framing shaped the UX intent, not just the graph mechanics.

Lock Protocol

Each decision below was tested against a counter-argument before being locked. Some were initially proposed differently and corrected. The correction is documented. If you believe a locked decision is wrong, bring evidence — not preference.

Locked Decision 1 — GPS Navigator Analogy

The engine is a GPS navigator for UI configuration, not a document search or lookup table. Every response gives exact portal, exact left-nav, exact tab, exact field, exact value, exact button — per step, version-pair aware. This analogy governs all UI and UX decisions downstream. See Tab 1: System Design.

Locked Decision 2 — 3-Layer Confidence, Weights 0.3 / 0.4 / 0.3

Ported from the Cisco EN CLI Agent. Weights: c_doc=0.3, c_gui=0.4, c_lab=0.3. Formula: Σ(w×c)/Σ(w). Do NOT change weights without testing against known-good step pairs. Renormalises when c_lab absent. See confidence formula in transition guide.

Locked Decision 3 — 17-Agent System (12 Nodes + 5 Supporting)

Simplification to fewer nodes was proposed and rejected. All 12 LangGraph nodes are required. The 5 supporting agents (Playwright Scraper, PDF Ingestor, Gap Curator, Version Manager, Schema Migrator) are not optional. Do not collapse nodes to reduce complexity. See Tab 2: Agentic Architecture.

Locked Decision 4 — Version-Pair Architecture

All mappings tagged to exact version pair. XIQ-25.8.0→EP1-25.9.0 stored entirely separately from XIQ-25.8.0→EP1-25.9.2. When EP1 ships a patch, admins trigger re-scrape — new pair is new data, not an overwrite. The engine ages gracefully as EP1 evolves without corrupting past records.

Locked Decision 5 — Neo4j for Graph Traversal + pgvector for Semantic Search

These are different tools for different data structures. Neo4j is for workflow graphs (traversal, path planning, edge weight storage). pgvector is for semantic search over documents and confirmed examples. They are not interchangeable and must both be present. See Tab 1: Tech Stack.

Locked Decision 6 — Two-Phase Node 0 (Path Planner + Orchestrator)

Node 0 operates in two phases. Phase 1 (PLAN): reads full Neo4j path before any execution — computes path_confidence, identifies gap edges, generates route_preview, pauses at HITL gate. Phase 2 (EXECUTE): only after user confirms. This is the structural encoding of learning. See Node 0 correction below and Tab 2: Agentic Architecture.

Locked Decision 7 — HITL at Two Levels

HITL is not optional and is not just for gap correction. Level 1: upfront confirmation gate — Node 0 shows route_preview before any step fires. Level 2: mid-traversal pause — Node 6 interrupts at gap edges for curator review. As stated: agents cannot deliver 100% guarantee; HITL is the formal safety net. Even Google Maps requires the driver to confirm the route.

Learning Framework

How the Engine Learns and Gets Better — Four Mechanisms

The Fundamental Insight

Two types of knowledge serve different purposes. Structural knowledge lives in Neo4j edge properties — the road quality map the engine reads before it moves. Semantic knowledge lives in pgvector — the pattern library the LLM draws on to explain, translate, and give context. Both grow independently. Both are required. Neither alone is sufficient for an anticipatory, self-improving system. See Tab 5: Learning & Growth.

TypeWhere It LivesWhat It EnablesHow It Grows
StructuralNeo4j MAPS_TO edge properties: confidence, c_doc, c_gui, c_lab, traversal_count, success_count, last_validatedNode 0 anticipatory path planning — reads road quality before traversal begins. The graph IS the memory.Lab runs update c_lab; scrape diffs restructure edges; curator corrections rebuild edges
Semanticpgvector: rag_chunks (14 PDFs) + confirmed_examples (curator + lab validated)LLM translation quality — few-shot context for Node 4, explanation grounding for user-facing outputPDF re-ingestion on doc update; curator corrections add high-weight examples (weight=2.0)

The Four Learning Mechanisms

#MechanismTypeTriggerEffect on the Engine
1 Lab Validation Structural Node 10 executes config on live lab, passes/fails update_c_lab(c_lab_prev, passed, n) updates c_lab on Neo4j edge. 5 passes → c_lab ≈ 1.0. One fail from 0.8 → 0.64. Trust earned slowly, lost quickly.
2 EP1 Patch — Graph Growth Structural Admin triggers re-scrape after new EP1 release Playwright finds new screens → new Neo4j nodes + edges under new version pair. Previous pair preserved. Engine map expands without history loss.
3 Few-Shot Accumulation Semantic Curator or lab confirms a mapping Row added to confirmed_examples with source, weight, version_pair. Node 4 (EP1 Translator) pulls nearest neighbours via pgvector cosine → improves translation quality over time.
4 HITL Curator Correction Structural Semantic Curator flags wrong nav path or missing step Neo4j edge restructured (structural fix) + new confirmed_example added with weight=2.0 (semantic fix). Dual-layer correction — map corrected and translator learns the right answer simultaneously.

The update_c_lab() Formula — Why Asymmetry Matters

def update_c_lab(c_lab_prev: float | None, passed: bool, n: int) -> float:
    result = 1.0 if passed else 0.0
    if c_lab_prev is None:
        return result
    return (c_lab_prev * (n - 1) + result) / n

# Trust earned slowly:   5 passes from zero  →  c_lab = 1.0  ("battle-tested")
# Trust lost quickly:    c_lab=0.8, one fail  →  (0.8×4+0)/5 = 0.64  (drops to WARN)
# Recovery is hard:      0.64, one pass       →  (0.64×5+1)/6 ≈ 0.70  (barely back to HIGH)
# Multiple passes to recover — by design. One failure flags curator review.

This is implemented in app/agents/node_05_confidence.py and validated by 8 tests in tests/test_learning.py. The asymmetry is intentional: a mapping that fails in a real lab should not be silently recovered by a single re-pass.

Node 0 — The Architectural Correction

From Reactive Retrieval to Anticipatory Path Planning

The Original Design — What Was Wrong

The original design used confirmed_examples (pgvector semantic search) as the primary learning mechanism. Node 0 would retrieve similar past mappings, use them as context, and execute step-by-step. This is reactive — it finds similar past trips but gives Node 0 no awareness of the road quality ahead on the current route.

It is the equivalent of a GPS that can only show you routes taken before. If road quality on your specific route has degraded since the last trip, the GPS cannot warn you before you drive.

The Correction — Structural Memory in Graph Edges

Learning must be encoded in the graph, not retrieved from a separate store. The Neo4j MAPS_TO edge properties (confidence, c_lab, traversal_count, success_count, last_validated) ARE the encoded structural memory. Node 0 must read the full route quality map before moving a single step — exactly as Google Maps reads real-time and historical traffic data before generating a route.

confirmed_examples remains valuable — but as a semantic layer for LLM translation quality, not as the primary learning mechanism for path planning.

Node 0 — Two-Phase Design (Sprint D Implementation)

PhaseWhat HappensOutput to State
Phase 1: PLAN Full Cypher path traversal reads all MAPS_TO edge weights for the entire route before execution begins. Computes path_confidence = min(edge.confidence) — the worst bottleneck. Identifies gap_edges (<0.40) and warn_edges (0.40–0.70). Generates human-readable route_preview with per-step confidence. planned_route, path_edge_weights, path_confidence, route_preview → HITL gate
Phase 2: EXECUTE Only after hitl_gate_passed = True. Routes to Node 1 (Intent Parser) to begin step-by-step execution. Every step already has its expected confidence — no surprises mid-route. Full workflow traversal with pre-validated confidence per step

The Cypher Path Query — Reading the Road Quality Map

MATCH path = (start:XIQScreen {screen_id: $seed_id})
             -[:MAPS_TO*]->
             (end:EP1Screen {screen_id: $destination_id})
WHERE ALL(r IN relationships(path) WHERE r.version_pair = $version_pair)
RETURN path,
       [r IN relationships(path) | r.confidence] AS edge_confidences,
       reduce(min_c = 1.0, r IN relationships(path) |
              CASE WHEN r.confidence < min_c THEN r.confidence ELSE min_c END
       ) AS path_confidence,
       [r IN relationships(path) WHERE r.confidence < 0.40  | r] AS gap_edges,
       [r IN relationships(path) WHERE r.confidence >= 0.40
        AND r.confidence < 0.70 | r] AS warn_edges

The query returns the entire route quality map in a single Cypher call. path_confidence is the minimum confidence across all edges — the weakest link. Gap edges are surfaced immediately so the route_preview can warn the user before any execution begins. See Tab 2: Agentic Architecture → Neo4j Edge Schema.
