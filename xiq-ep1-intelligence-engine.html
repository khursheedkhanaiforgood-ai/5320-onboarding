Vision

What This System Does

When a network engineer asks "how do I configure CWP for PPSK in EP1?" or "show me the AP VLAN tagging workflow," they get an exact, screen-by-screen guide: which portal, which left-nav item, which dropdown value, which field label, which button to click — not a generic document reference. The system knows the answer for a specific version pair (XIQ 25.8.0 → EP1 25.9.0) and tells you when EP1 doesn't have a direct equivalent and what to do instead.

Core Analogy

It is a GPS navigator for UI configuration. XIQ is your starting map. EP1 is your destination. The engine knows every road, one-way street, and detour — including roads that EP1 hasn't built yet (gaps).

Two Query Types — Always Classified First

Every user query enters a classifier before any graph traversal. This determines response depth:

Query TypeExampleResponseGraph Operation
workflow "Show me the AP VLAN tagging workflow" Full multi-step sequence: each step is one screen card (portal → nav → field → value → button) Full LangGraph traversal — XIQ subgraph → translation → EP1 subgraph
lookup "Which menu do I use to configure CWP for PPSK?" Single screen card: nav path + field label only. No step sequence. Single Neo4j node lookup by intent keyword → return nav_path + screen_id
compare "What's different between XIQ and EP1 for switch policy?" Side-by-side diff table: XIQ steps on left, EP1 on right, gaps highlighted Both subgraphs fetched, diff computed at Node 5

Confidence Formula (from Cisco EN CLI Agent)

confidence = Σ(w × c) / Σ(w)  →  c_doc×0.3 + c_gui×0.4 + c_lab×0.3

Each layer scores 0.0–1.0. A step with c=0.95 has been documented, found in UI, and lab-verified. A step with c=0.40 exists in docs but scraper didn't find it → likely restructured or gap.

Version Control

Version-Pair Architecture

All mappings, screenshots, and confidence scores are tagged to an exact version pair. A workflow confirmed for XIQ 25.8.0 → EP1 25.9.0 is stored separately from XIQ 25.8.0 → EP1 25.9.2. Users pick their pair from a top-nav dropdown. Admins trigger re-scrapes when a new EP1 patch ships.

Overview

17-Agent System — Plan First, Then Execute

12 LangGraph nodes form the stateful execution graph. Node 0 is not just a router — it is a path planner. Before any traversal begins, it computes the full path confidence using Neo4j edge weights, identifies low-confidence steps, and surfaces HITL checkpoints upfront. The agent never walks blind. 5 supporting agents run outside the graph as standalone services.

Google Maps Analogy — How This Engine Actually Navigates

Google Maps does not reason from first principles to find a route. It executes a shortest-path algorithm over a pre-encoded weighted graph where every road has quality metrics. Our engine works the same way: Neo4j is the road network, edge confidence weights are the road quality, and Node 0 is the routing algorithm. Learning = updating edge weights. The graph IS the memory. A step validated 12 times in the lab has a high-weight edge — the agent "knows" it's a safe road before it takes it.

LangGraph Nodes (0–11)

Node Descriptions

Node 0

Path Planner + Orchestrator

Phase 1 — Plan: After Node 1 returns the XIQ seed node, Node 0 runs a full Neo4j path traversal, reads all edge weights, computes path_confidence = min(edge.confidence), identifies low-confidence and gap edges, generates a "route preview," and presents a HITL confirmation gate before any step executes. User sees what's coming — no surprises. Phase 2 — Execute: routes through Nodes 1–9. Manages retry and error escalation.

Node 1

Intent Parser

pgvector semantic search over RAG corpus → candidate XIQ feature nodes. Classifies query: workflow | lookup | compare. Lookup short-circuits to Node 7. Compare routes to dual subgraph fetch.

Node 2

XIQ Workflow Builder

Neo4j traversal of XIQ subgraph from Node 1 seed node. Expands full step sequence. Each step includes: screen_id, nav_path, field_label, input_value, button_label, screenshot_ref.

Node 3

Version Resolver

Filters all graph traversals to the active version pair from user session. Prevents cross-version contamination. Logs version pair on every execution_log entry.

Node 4

EP1 Translator

For each XIQ step: (1) pgvector search over 14 PDFs → c_doc score; (2) Neo4j lookup → c_gui score; (3) pgvector search on confirmed_examples → top-5 similar confirmed mappings → injected as few-shot context into Claude prompt. This is the learning mechanism — translations improve as the example store grows.

Node 5

Confidence Aggregator

Computes per-step confidence: Σ(w×c)/Σ(w). Weights: c_doc=0.3, c_gui=0.4, c_lab=0.3. When c_lab is absent (not yet lab-validated), renormalises to c_doc=0.43 + c_gui=0.57. Emits confidence tier: HIGH ≥0.80, MED 0.50–0.79, LOW <0.50.

Node 6

Gap Detector

Any step with confidence <0.40 → GAP (route to Node 9). Steps 0.40–0.69 → WARN (flag in UI, continue). Steps ≥0.70 → OK. Detected gaps auto-staged for Gaps Register (bin + description + workaround TBD).

Node 7

Nav Path Generator

Builds the screen card for each step: portal URL prefix, left-nav path, tab name (if any), field label, dropdown option or text value, submit button label. This is the GPS turn-by-turn output.

Node 8

Response Formatter

Assembles final output by query type: full workflow (ordered step cards + confidence badges), single lookup card, or side-by-side diff table. Attaches screenshot thumbnails where available.

Node 9

Fallback Agent

Activated on GAP. Queries RAG: "what does EP1 documentation suggest as workaround?" Generates Supplemental CLI block or manual steps as alternative. If no workaround found → escalates to Gap Curator (supporting agent).

Node 10

Execution Agent

Optional node (admin-only, requires live lab). Pushes the generated EP1 configuration to real hardware. Captures CLI output. Compares each anticipated value to actual. Updates c_lab per step. On failure: routes to Node 11.

Node 11

Feedback Loop

Processes Execution Agent result. Success: c_lab updated via weighted running average (converges to true reliability over N runs) → write to confidence_score → write to confirmed_examples (source=lab) → log to query_log. Failure: c_lab drops → auto-create gap → flag Neo4j node BROKEN → notify Gap Curator → Gap Curator correction written to confirmed_examples (source=curator, weight=2×).

Out-of-Graph Services

Neo4j Edge Schema — The Encoded Memory

Road Quality Metrics on Every Edge

The confirmed_examples store handles semantic similarity (finding analogous past routes). But structural learning — "this road has been driven safely 12 times" — lives as edge properties in Neo4j. This is what gives Node 0 anticipatory capability: it reads these properties before traversal begins and knows which roads are safe, which are unpaved, and which don't exist yet.

// Every XIQ→EP1 mapping edge carries road-quality metrics
(xiq_node:Screen {screen_id: "xiq.network_policy.ssid.auth.ppsk"})
  -[r:MAPS_TO {
    // ── confidence (the road quality) ─────────────────────
    confidence:       0.87,   ← current weighted score — what Node 0 reads for path planning
    c_doc:            0.80,   ← what EP1 documentation says about this path
    c_gui:            0.90,   ← what Playwright confirmed in the UI
    c_lab:            0.85,   ← empirical: how many times this road was driven safely

    // ── traversal history (the learning) ──────────────────
    traversal_count:  12,     ← total attempts on this road
    success_count:    11,     ← successful traversals (1 failure → c_lab pulled down)
    last_validated:   "2026-05-21",
    source:           "lab",  ← highest-quality: lab > curator > scrape > doc

    // ── versioning ─────────────────────────────────────────
    version_pair:     "XIQ-25.8.0__EP1-25.9.0",
    ep1_patch:        "25.9.0"
}]->(ep1_node:Screen {screen_id: "ep1.network_policy.wireless.ssid.auth.ppsk"})

// When EP1 patches and nav path changes — edge is RESTRUCTURED, not deleted
(ep1_node_v0)-[r2:RESTRUCTURED_TO {
    from_version: "25.9.0", to_version: "25.9.2",
    confidence:   0.0   ← c_gui reset — must be re-earned after path change
}]->(ep1_node_v2)

// A gap — the road doesn't exist (yet)
(xiq_gap_node)-[r3:GAP {
    gap_code: "G-01", severity: "high",
    workaround: "CLI: unconfigure switch all"
}]->(:GapNode {description: "EXOS factory reset not available in EP1"})

How Node 0 Uses Edge Weights for Path Planning

# Node 0 path planning — runs BEFORE any step execution
MATCH path = (start:XIQScreen {screen_id: $seed_id})
             -[:MAPS_TO*]->
             (end:EP1Screen {screen_id: $destination_id})
WHERE ALL(r IN relationships(path) WHERE r.version_pair = $version_pair)
RETURN path,
       [r IN relationships(path) | r.confidence] AS edge_confidences,
       reduce(min_c = 1.0, r IN relationships(path) | CASE WHEN r.confidence < min_c THEN r.confidence ELSE min_c END) AS path_confidence,
       [r IN relationships(path) WHERE r.confidence < 0.40 | r] AS gap_edges,
       [r IN relationships(path) WHERE r.confidence >= 0.40 AND r.confidence < 0.70 | r] AS warn_edges
# Result: Node 0 knows the full route quality map before taking one step
# "You have 6 steps. Step 3 is unpaved (WARN). Step 5 is a dead end (GAP)."

Why Automate Validation

The Execution Agent Closes the Loop

Documentation says one thing. The UI shows another. But does the configuration actually push correctly? The Execution Agent (Node 10) answers that question by deploying the generated policy to live hardware and comparing field-by-field. Without this, confidence is theoretical. With it, confidence is empirical.

The second reason is drift. EP1 ships patches roughly every 6 weeks. A nav path that worked in EP1 25.9.0 may have moved in EP1 25.9.2. Automated re-validation catches this before a user hits it in production.

Version Drift Detection

What Happens When EP1 Ships a Patch

Drift Scenario

EP1 25.9.2 ships. The CWP configuration screen moves from Configure → Network Policies → [policy] → SSIDs → [ssid] → User Authentication → CWP to a new top-level Configure → Captive Portal → Profiles path. Users following the 25.9.0 workflow hit a dead end.

The Version Manager (Support Agent 4) handles this:

  1. Admin registers EP1 25.9.2 via admin UI → triggers diff-scrape
  2. Playwright scraper runs on EP1 25.9.2 → captures all screens
  3. Diff engine compares Neo4j nodes: EP1-25.9.0 vs EP1-25.9.2
  4. Changed nodes flagged as RESTRUCTURED — old nav_path deprecated, new path set
  5. Confidence scores for affected steps reset: c_gui=0.0 pending re-validation
  6. Gap Curator reviews staged changes → approves or escalates
  7. Users on EP1-25.9.2 version pair immediately see updated nav paths
Confidence Tiers

What Confidence Means to the User

TierScoreMeaningUI Treatment
HIGH ≥ 0.80 Documented + found in UI + lab-verified. Safe to follow. Green badge, no annotation
MED 0.50 – 0.79 Documented + found in UI, but not yet lab-validated OR minor discrepancy. Amber badge, "verify in lab" note
LOW 0.40 – 0.49 RAG says it exists but UI evidence is weak. May be restructured. Red badge, "path may have changed" warning

The Honest System Principle

This engine must be more honest than a human consultant. A consultant might guess or omit uncertainty. This system shows the confidence score on every step. A gap is not a failure — it is the most valuable output: it tells the engineer exactly where EP1 is not ready and gives them a workaround rather than a dead end.

Design Principle

Learning Must Be Encoded, Not Retrieved

A critical architectural distinction: there are two types of knowledge, and they must not be confused.

TypeWhere it livesWhat it enablesGoogle Maps equivalent
Structural learning Neo4j edge properties (confidence, traversal_count, success_count) Node 0 anticipates the full path before taking a step. Knows which roads are safe, unpaved, or missing. Road network with traffic/quality weights — the route algorithm runs over this
Semantic learning pgvector (RAG corpus + confirmed_examples) Node 4 explains steps in context. Finds analogous past mappings to improve LLM translations. POI names, address geocoding — helps interpret "go to Starbucks," not find the road

The confirmed_examples store was initially framed as the primary learning mechanism. That was wrong. It is the semantic layer — useful for LLM context injection in Node 4. The primary learning mechanism is the graph edge weights. When a path has been traversed successfully 12 times, that fact is encoded in success_count=12 and confidence=0.92 on the Neo4j edge. Node 0 reads those properties and knows — before moving — that this road is safe. That is anticipatory navigation, not reactive gap discovery.

Learning operates at four distinct timescales, each with its own mechanism. None require retraining a model. The graph IS the memory.

Auditability Requirement

Every learned fact must be traceable. When confidence changes, the reason must be queryable: "This step's c_lab moved from 0.3 to 0.7 because the Execution Agent ran it successfully 4 times between May 21 and June 10, with CLI output saved in execution_log rows 47, 52, 61, 68." No black-box learning. Every update has a source, a timestamp, and a human-readable reason.

Mechanism 1 — Empirical Confidence (Lab-Driven)

Node 11 currently does c_lab += 0.1 per successful run. The full implementation uses a weighted running average: after N successful runs the score converges toward the true reliability of the step. Failures pull it back. The formula:

# c_lab converges to true reliability over N runs
c_lab_new = (c_lab_prev * (n-1) + result) / n
# result = 1.0 on pass, 0.0 on fail
# after 5 passes: c_lab ≈ 1.0  |  after 1 fail from 0.8: c_lab drops to 0.64

# "Battle-tested" threshold: 5+ successful runs with c_lab ≥ 0.90
# UI shows ⚔ badge — independently validated, not just documented

Mechanism 2 — Knowledge Graph Growth (Version-Driven)

The Neo4j graph is the living map. When EP1 25.9.2 ships:

  1. Version Manager registers new version → triggers Playwright diff-scrape
  2. Scraper runs against EP1 25.9.2 → captures all screens
  3. Diff engine: compares every node between 25.9.0 and 25.9.2 → flags RESTRUCTURED (nav path changed), ADDED (new feature), REMOVED (feature dropped)
  4. Neo4j updated: old nodes deprecated, new nodes added, RESTRUCTURED edges drawn
  5. c_gui reset to 0.0 on changed nodes — confidence must be re-earned
  6. Users on 25.9.2 version pair immediately see updated nav paths; users on 25.9.0 pair unaffected

The graph never stagnates. Each version is a snapshot; the engine holds all snapshots simultaneously and serves the right one based on session context.

Mechanism 3 — Analogical Learning (Few-Shot Accumulation)

This is the most powerful learning mechanism. Node 4 (EP1 Translator) currently does a pgvector search over RAG + a Neo4j lookup per step. Extended Node 4 adds a third retrieval: the Confirmed Examples Store.

New XIQ step arrives at Node 4: "Configure → Network Policies → [policy] → SSIDs → [ssid] → User Auth → CWP → Self-Reg" │ ▼ Step 1: embed XIQ step description → 1536-dim vector ▼ Step 2: pgvector search on confirmed_examples → top-5 most similar confirmed XIQ→EP1 mappings │ │ Example hit: "Configure → [policy] → SSIDs → [ssid] → User Auth → PPSK" │ → EP1: "Configure → [policy] → Wireless → SSIDs → [ssid] → Auth → PPSK" │ → confirmed by lab, c_lab=0.92, source=lab, run=5x ▼ Step 3: inject as few-shot context into Claude prompt "Here are 5 confirmed XIQ→EP1 mappings structurally similar to this step. Use their patterns to infer the EP1 equivalent of the new step." ▼ Step 4: Claude generates EP1 nav path → grounded in empirical evidence, not just documentation

As more workflows are validated — in the lab, by curators, by Playwright scrapes — the example store grows. Month 3 Node 4 is measurably better than Month 1 Node 4 on unseen workflows. This is learning by analogy — the same mechanism expert engineers use.

Mechanism 4 — Human-in-the-Loop (Two Levels, Not One)

Agents cannot deliver 100% guarantee. HITL is the formal acknowledgment of that — not a workaround, but a design principle. Like Google Maps where you still confirm the route and destination before driving, the engine presents human verification opportunities at two levels:

  • Level 1 — Upfront confirmation gate (Node 0): Before any step executes, the route preview surfaces all low-confidence and gap edges. "This workflow has 6 steps. Steps 3 and 5 require your attention before we begin." User confirms or requests alternative.
  • Level 2 — Mid-traversal pause (Node 6 + Gap Curator): If a gap edge is encountered during execution, the graph pauses, surfaces the state, and waits for curator confirmation before continuing.

LangGraph's HITL feature (interrupt/resume with checkpointer) implements both levels natively.

Gap Detector (Node 6) flags confidence=0.28 ▼ State saved to PostgreSQL checkpointer (full XformState at this point in the run) ▼ Gap Curator UI surfaces the step: "Node 4 proposed: Configure → [policy] → Wired → Switch Templates → VLANs" "Confidence: 0.28 (LOW). Is this correct?" │ ├── CORRECT ──▶ confirmed_examples.add(source='curator', weight=1.0) → resume │ └── WRONG ──▶ Curator types corrected nav path ▼ confirmed_examples.add(corrected_path, source='curator', weight=2.0) Neo4j: update node nav_path gap.status = 'resolved' or 'workaround' Graph resumes from checkpointed state with corrected path
Why curator corrections get weight=2.0

A human expert saying "this is wrong, the correct path is X" is the highest-quality signal in the system. It outweighs a PDF citation (c_doc) and outweighs a Playwright scrape (c_gui) because it represents ground truth validated by domain knowledge. The 2× weight ensures this signal propagates strongly into future translations via few-shot retrieval.

Independent Assessment

Every confidence score, every learning event, every curator correction is stored with a timestamp, a source, and a reason. An independent assessor can query: "Show me all steps where confidence changed between May 21 and June 21 — what caused each change?" The answer is a SQL query over confidence_score, execution_log, confirmed_examples, and query_log. Nothing is hidden. Nothing is inferred from a black box. The system is accountable at every layer.
