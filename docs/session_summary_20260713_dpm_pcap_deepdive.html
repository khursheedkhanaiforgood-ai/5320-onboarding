§4 — Cisco RRM Logic, EN's Validation Gap & the Aerohive Legacy Find

Cisco's published RRM algorithm (the "logic, not values" ask)

Read the DCA and TPC sections of a Cisco RRM White Paper already sitting in the local WLPC corpus.

DCA: single Cost Metric (CCI + foreign-channel + noise + channel load)
     → CPCI (worst AP first, then random) → evaluate 1st/2nd-hop neighbors only
     → NCCF gate (only change if CPCI improves AND neighbors don't regress)
     → 10-20dB sensitivity threshold (hysteresis, prevents flip-flopping)

TPC: Tx_ideal = Tx_max + (Power_Threshold − RSSI_3rd_neighbor)
     Power derived from the 3rd-loudest neighboring AP, not client RSSI

EN vs. Cisco RRM — deficiency analysis, with a caveat: everything confirmed about EN's AutoRF is simpler — independent flat thresholds (35%/35%/35%) instead of one weighted Cost Metric, no documented neighbor-impact gating, no documented dynamic TX-power formula. But this may partly reflect documentation opacity (Cisco publishes an algorithm; EN's public docs describe configurable fields, not XIQ Cloud RRM's actual cloud-side logic) rather than proven algorithmic inferiority.

The EN validation gap — confirmed empirically, not assumed

Grepped the entire 33,261-line Extreme_Platform_ONE_Networking_25_9_0_User_Guide.pdf for "capacity planning," "predict," "site survey," "mall," "retail," "dense urban" — zero hits on every term. EN's own "Client SLA" mechanism is a reactive, post-hoc, per-client health-scoring system (Rate/Success/Usage targets + Log/Boost-Airtime actions) — not a pre-deployment predictive tool.

Major find: the Aerohive 2013 High-Density Wi-Fi Design Guide

AP3000 is Aerohive/HiveOS-heritage hardware. Found and read a legacy Aerohive design guide (Andrew von Nagy — same author as the Revolution Wi-Fi Capacity Planner already in the local corpus) with a real capacity-forecasting formula and a documented forecast→verify loop via predictive RF site survey.

airtime_per_device = throughput_target ÷ max_achievable_throughput
devices_per_radio  = 80% ÷ airtime_per_device
radios_required    = (device_count × airtime_per_device) ÷ 80%

Also revealed the SLA remediation toolkit is actually 3-pronged (airtime boost + band steering + client load balancing — the engine is literally named "Dynamic Airtime Scheduling"), broader than what current EP1 docs describe. This methodology appears to have been dropped from current EN/XIQ documentation — the old Aerohive docs URL now 301-redirects to a generic support landing page.

Open gap flagged: the DigitalTwinEngine's 5 existing archetypes (Stadium, Enterprise, Hospital, Warehouse, Residential) don't include dense-urban retail/mall — the scenario actually discussed. Worth adding as a 6th archetype.

§5 — The 4-Way Handshake, Live: A Ground-Up Wireshark Study

Opened Wireshark and walked a single reference capture, wpa-4way-handshake.pcap, from Beacon through encrypted data — rejecting two other candidate files (lab11.pcapng, intuitibits.pcapng) after tshark analysis showed both were scattered multi-client aggregates rather than one coherent story.

The corrected sequence (client repeatedly reconstructed it, corrected each time with evidence)

Beacon (always on, continuous)
  → Probe Request/Response          (#58-74,  t≈5.18-5.33s)
  → Authentication (open, empty)    (#78, 80, t≈5.64s)
  → Association Request/Response    (#82, 84, t≈5.645-5.647s)
  → 4-way EAPOL handshake           (#87-94,  t≈5.65-5.66s)
  → Encrypted data                  (#99+)

Association vs. Probe — the distinguishing elements

Pulled real field content via tshark -V. The two elements that exist only in Association Response, never in Probe Req/Resp:

FieldValue (frame #84)Significance
Status CodeSuccessful (0x0000)Explicit accept/reject — Probe has no such concept
Association ID0x0001Unique per-client handle the AP now tracks — real state creation

The full handshake, byte by byte

MsgReal fields (tshark -V)What it proves
1 (#87)ANonce sent, Key ACK=Set, MIC=Not setNo MIC yet — KCK doesn't exist until both nonces are exchanged
2 (#89)SNonce + MIC=Set, 22-byte plaintext Key Data (client's RSN IE)First real proof-of-PSK-knowledge; RSN IE re-sent to defeat downgrade attacks on the unprotected Association exchange
3 (#92)Install=Set, MIC=Set, Encrypted Key Data=Set, 80 bytesEncrypted GTK delivered, wrapped in KEK — the only message with real encryption, not just signing
4 (#94)MIC=Set, Nonce=all-zero, Key Data Length=0Pure confirmation — both sides now install PTK+GTK, controlled port opens

Five corrected misconceptions

  1. PTK is never transmitted. Both sides independently derive it — client right after Msg1 (needs KCK for Msg2's MIC), AP right after Msg2 (needs KCK+KEK for Msg3).
  2. MIC does not encrypt. It's a signature (KCK-based). The RSN IE in Msg2 travels in plaintext, readable directly in Wireshark.
  3. GTK is not derived from PTK. Separate root key — the GMK, generated independently by the AP: GTK = KDF(GMK, AP_MAC || GNonce). PTK's KEK sub-key is only the delivery wrapper.
  4. GTK delivery is per-client, not one broadcast. New clients get it in their own Msg3; already-connected clients get a rotated GTK via a separate, shorter 2-message Group Key Handshake.
  5. GTK isn't continuously regenerated — event-triggered (timer or client departure), static in between.

CCMP Key Index — the on-the-wire proof of which key was applied: Key Index 0 = pairwise (PTK), always, universally. Key Index 1-3 = group (GTK). Confirmed directly: frame #102 (unicast AP→client) shows Key Index 0; every AP-originated broadcast frame in this capture (10 instances checked, all to the 802.1D bridge-group address 01:80:c2:00:00:00) consistently shows Key Index 2. Along the way, found that the AP uses two different source MACs — one for beacons/handshake (...b2:55), a separate one for actual data-plane traffic (...b2:53) — a real multi-radio addressing quirk that broke the first filter attempt.

Why a client needs GTK despite already having PTK

PTK is architecturally one-to-one; using it for broadcast would require N separate transmissions per frame, defeating the entire purpose of broadcast. GTK is one shared secret — encrypt once, every client (each with a different PTK) decrypts the same transmission. Required for ARP, DHCP broadcast stages, and multicast (mDNS, IPv6 ND).

GTK rekey overhead in dense networks

GTK delivery fan-out scales linearly with client count (≈2×N frames per rekey event), and the rotation timer typically fires BSS-wide simultaneously — a burst that contends with the WMM/EDCA mechanics from earlier in the day, and can desync clients via the same lost-ACK/retry mechanism observed directly in this capture's Probe Response forensics (a Probe Response was retransmitted 7 times — matching the standard 802.11 short-retry-limit convention). This is exactly the kind of second-order effect the still-missing mall/retail archetype (§4) would need to model.

§7 — LinkedIn Post Review

Reviewed a post by Harish Kumar sharing a 7-rule custom system prompt for Claude, built around the thesis "a wrong answer delivered confidently is worse than no answer."

Strongest point, proven live in this exact session: Rule 6 ("never invent function names/API syntax") — earlier in §5, eapol.keydes.msgnr was guessed as a Wireshark field name and was wrong. The real field, wlan_rsna_eapol.keydes.msgnr, was only found by running tshark -G fields and verifying before it was handed over. That's the rule working in its strongest form: actual verification, not verbal hedging.

Weaknesses flagged: "Claude stops lying to you" mischaracterizes hallucination as intentional deception rather than miscalibrated confidence. "Works in every chat, forever" oversells a system prompt's reliability. Rule 7 (always ask clarifying questions), applied indiscriminately, has a real usability cost for low-stakes questions. Packaging is standard engagement-bait, orthogonal to content quality.
