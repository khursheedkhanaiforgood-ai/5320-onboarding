AP2 Onboarding — AH-565780

Problem: AP Dark on Port 5

AP2 was plugged into SW1 port 5. show inline-power info ports 5 showed "delivering class4 at 1.1W" but AP LEDs were dark. 1.1W = detection current only, not operational. Cable reseat resolved — AP booted normally (orange → white).

Wrong VIQ

AP2 was previously registered on a different VIQ. After boot it entered SULKING state (900s pause) after failing to reach the old CAPWAP server. Factory reset performed via serial console:

reset config

Default credentials post-reset: admin / aerohive (or Aerohive1).

Serial Number Mix-up

First claim attempt in EP1 used wrong serial number — a different AP (AH-901340) briefly appeared in EP1 with IP 172.16.0.147 (from old VIQ). Correct serial confirmed via console prompt: AH-565780. Re-claimed with correct serial, reset config again, AP connected immediately.

Post-Connect Reboot

AP2 rebooted ~3 minutes after first connecting to VIQ. No network policy was manually pushed. Likely cause: EP1 auto-pushed a firmware upgrade on first claim. Normal behavior — wait for reboot to complete and re-verify connection.

SW1 DHCP + ipforwarding

VLAN Tag Conflict

Old VLANs (Ten=tag10, Twenty=tag20, etc.) blocked EP1 Supplemental CLI from creating new VLANs (TeamUSA=tag10, etc.). Fix: added delete commands at top of Supplemental CLI before create commands.

DHCP Enable — Correct Syntax

enable dhcp-server is invalid on EXOS. Correct command:

enable dhcp ports 3,5 vlan TeamUSA
enable dhcp ports 3,5 vlan TeamAUS
enable dhcp ports 3,5 vlan Guest
enable dhcp ports 3,5 vlan VIP
enable dhcp ports 3,5 vlan POS

ipforwarding = Internet

Clients had DHCP but no internet. Fix: enable ipforwarding — enables inter-VLAN routing and default gateway forwarding. Run once manually. Not idempotent — stalls EP1 push if included in Supplemental CLI.

Idempotent: A command that produces the same result whether run once or many times. enable ipforwarding and enable dhcp on EXOS are NOT idempotent — second run throws an error. EP1 Supplemental CLI runs on every push — non-idempotent commands must be run once manually only.

EP1 Stale Cache + MAC Randomization

Real-world XE-08 scenario played out in the lab with a second complication.

What Happened

  • EP1 showed phone and MacBook associated to AP1 (192.168.0.12)
  • SSH to AP1 → show station → NO clients
  • SSH to AP2 → show station → NO clients
  • MacBook confirmed on correct SSID with valid IP 10.30.0.102
  • Both APs physically 6 inches apart — client must be on one of them

Dual Root Cause

  1. EP1 stale cache — AP2 came online, client may have roamed. EP1 still showed old association on AP1 and hadn't refreshed.
  2. macOS MAC randomization — macOS rotates MAC address per SSID on reconnect. The cached MAC 74a6:cd8b:1960 was no longer the MAC the MacBook was using. New MAC discoverable via networksetup -getmacaddress en0.
Rule: show station on the AP is always authoritative. EP1 client view is cached and can lag. When EP1 and AP disagree, trust the AP. When a client is missing, check all APs and verify current MAC on the client device.

Diagnostic Chain for Missing Client

  1. show station on ALL APs — not just the one EP1 points to
  2. networksetup -getmacaddress en0 on MacBook — get actual current MAC
  3. show fdb ports 3,5 on SW1 — authoritative L2 MAC table
  4. show iparp vlan Guest on SW1 — cached MAC→IP even after roam
