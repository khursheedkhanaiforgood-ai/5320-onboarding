A2 — Monte Carlo Tab

Added to existing simulator  ·  commit 59cf038

Controls

  • Iterations: 100 / 200 / 500 / 1000
  • Demand CV: ±10% / ±20% / ±30% (coefficient of variation on per-client demand)
  • Pareto α: 1.5 / 2.0 / 3.0 (tail heaviness of demand distribution)

Pareto Demand Sampling

// Heavy-tail demand sampling
xm = (α − 1) / α                     // scale parameter
sample = xm × U^(−1/α)               // inverse-CDF method
sample = Math.min(sample, 3.5 × xm)  // cap at 3.5× to prevent runaway outliers

// Fan-count variation
fanCount = baseCount × (1 + (Math.random() − 0.5) × 0.30)  // ±15%

Output Metrics

P5 / P50 / P95 on: QoE score, airtime utilisation, E2E latency, POS latency, throughput/client. Three breach metrics:

  • P(airtime > 70%) — collapse probability
  • P(posLatency > threshold) — POS SLA breach rate
  • Score spread: P95 − P5 — robustness indicator

rTWT-aware POS threshold (added same day): When rTWT is ON, the POS breach threshold tightens from 10ms to 3ms. The model already computes posLat ≤ 3ms via rTWT hardware scheduling — the MC now enforces the correct SLA for each rTWT state independently. This prevents rTWT from appearing to "help" when the threshold is wrongly fixed at 10ms.

The optimizer directly implements the §03 robust objective without ns-3. It finds parameters that hold up at P95 demand — not just the median — making it the correct architecture for chance-constrained search regardless of whether ns-3 is eventually used.

Objective Function (Chance-Constrained)

maximize   P50[U(θ)] − 0.5 · (P95[U] − P5[U])

subject to P(posLatency ≤ threshold) ≥ 99%
           P(active_clients ≤ maxClients × 280 APs) ≥ 95%

where U(θ) = Σᵢ log(throughputᵢ)   over all admitted bulk clients

Locked-Out Parameters (Context-Modulated by Archetype)

GI = 1600 ns — τ_RMS in stadium outdoor mandates this. Adding GI to the search would be a category error: once you commit to the "stadium outdoor" archetype, τ_RMS is a regime constant, not a free variable.

MU-MIMO Streams = 8 — Angular spread is high in the bowl. 8-stream MU-MIMO is optimal by archetype. This is locked, not searched.

Client Ageout = 5 min — Stadium dwell time is long (3–4 hours). Aggressive ageout would strand fans with intermittent connectivity. Locked at 5 min.

Roam Cache Age = 60 min — Game duration. Locked to match event timeline.

Why MC-Inside Matters: The CWmin Example

Key Insight — Point-Estimate vs MC-Inside Optimizer

At CWmin=7, the point-estimate optimizer gets the wrong answer

At P50 demand (moderate load), CWmin=7 produces u≈0.62 — below the collision cliff. The point-estimate optimizer sees a fine score and picks CWmin=7.

At P95 kickoff surge, the same CWmin=7 produces u≈0.81 → exponential collision burst → POS SLA breach at a rate that violates the 99% constraint. The MC-inside optimizer correctly observes this breach probability and penalizes CWmin=7, converging to CWmin=15 or 31.

The same logic governs TXOP-BE × rTWT interaction: the point-estimate model misses the starvation risk that only manifests at P95 demand with rTWT OFF.

Admitted-Count Constraint

// Priority order in objective
strandPenalty  = P(active > maxCli × 280 APs) × 20   // cannot strand fans
posPenalty     = P(posLat > threshold) × 50           // POS SLA is first-class
spreadPenalty  = 0.5 × (P95[U] − P5[U])              // robustness term

score = P50[U] − strandPenalty − posPenalty − spreadPenalty

§03 — Key Decisions Made Today

Decision 1 — Track Split

ns-3 deferred (Track B) — existing JS model ships immediately (Track A)

Rationale: No ns-3 install on this machine. The existing JS multiplier-chain model already captures threshold and interaction effects: CWmin cliff at u>0.7, TXOP×rTWT starvation risk, admission constraint. These are the mechanisms that matter for the optimizer.

Implication: Track A ships three usable artifacts today. Track B resumes when ns-3 is ready — the starter kit (stadium-wifi.cc + qoe_harness.py) is staged and waiting.

Decision 2 — Architecture: Both MC and Optimizer

Monte Carlo + Optimizer are complementary — not either/or

Rationale: MC finds the P95 exposure of any given parameter set θ. The optimizer finds the θ that minimizes that exposure while maximizing P50 utility. They compose: optimizer calls MC internally (MC-inside architecture). Running them separately would miss the robust objective.

Implication: The optimizer is not a search over point-estimates. It is a search over the distribution of outcomes under uncertain demand. This is the correct architecture for a stadium where kickoff surge can be 2× the P50 load.

Decision 3 — 12 Knobs Not 15

GI, MU-MIMO streams, client ageout, roam cache are context-modulated — locked by archetype

Rationale: These four parameters are determined by the deployment context (stadium outdoor), not by optimization. GI is mandated by τ_RMS. MU-MIMO streams are mandated by angular spread. Client ageout and roam cache are mandated by event duration. Including them in the search set would allow the optimizer to "discover" suboptimal archetypes.

Implication: Once you assign an archetype, regime constants are frozen. The optimizer searches within the archetype, not across archetypes.

Decision 4 — 5G Channel Width Added to Search Set

160 MHz vs 80 MHz is a genuine tradeoff in dense bowl — not monotone

Rationale: Wider channel → higher peak PHY rate per client. But in a dense 280-AP deployment, 160 MHz halves the number of non-overlapping channels, increasing inter-AP interference. The tradeoff is non-monotone: 80 MHz + more spatial reuse may outperform 160 MHz + fewer reuse opportunities at high density. Let the optimizer test both.

Implication: The optimizer now searches 80 vs 160 MHz on 5G. The result will be archetype-specific — a different result than for a sparse outdoor deployment.

Decision 5 — QoE = Proportional Fairness Under SLAs

U(θ) = Σ log(throughput) with hard POS/VIP/Teams constraints

Rationale: Proportional fairness (log-sum) prevents throughput monopolization at kickoff surge without requiring explicit per-client rate caps. The log utility function naturally allocates airtime fairly: doubling one client's rate while halving another's leaves the objective unchanged. Hard SLA constraints protect POS, VIP, and Teams service classes from fairness-driven preemption.

Implication: All future optimization targets this definition. Changes to the objective are governance events requiring a new CHANGELOG entry and a correction banner on the previous entry.

Decision 6 — rTWT Tightens POS Threshold to 3ms

When rTWT ON, POS SLA is 3ms — not 10ms

Rationale: rTWT (Restricted Target Wake Time for WiFi 7) allows the AP to schedule POS terminals in dedicated time slots with TDMA-like guarantees. The hardware can deliver ≤3ms latency when rTWT is active. Using the 10ms threshold with rTWT ON would make rTWT appear to have no effect on the POS breach rate — a false result.

Implication: The MC breach threshold switches dynamically: threshold = rTWT ? 3 : 10 ms. Both the Monte Carlo tab and the optimizer enforce this correctly.

Decision 7 — Admitted-Count Constraint Added

"Cannot strand fans" is a first-class constraint in the objective

Rationale: An optimizer without an admitted-count constraint can "win" by tightening Min RSSI so aggressively that thousands of fans are denied service. The score looks great but the deployment fails its primary mission.

Implication: strandPenalty = P(active > maxCli × 280 APs) × 20 is always present. Priority order: POS SLA (×50) > admitted count (×20) > utility spread (×0.5). The optimizer cannot trade access for SLA compliance.
