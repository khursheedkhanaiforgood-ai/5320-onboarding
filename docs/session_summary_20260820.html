D1 Socratic Dialogue — Full Q&A Record

Q1 — The Backbone Envelope

Q: When a client frame enters the fabric, two MAC addresses go into the outer Backbone header. What are they and where does each come from?

Your path: "Source and destination" → "from the MACs of each" (C-MACs) → corrected to B-MACs

Locked answer: B-SA = ingress BEB's own B-MAC (derived from IS-IS system-id). B-DA = egress BEB's B-MAC looked up in B-FIB. C-MACs (client source/destination) are sealed inside — the fabric core never sees them.

Breakthrough — The Outer Loop Never Changes

Q: Does the outer header change at each hop like traditional Ethernet?

Your answer: "So, all you need is go hop by hop" → corrected

Locked answer: B-SA and B-DA are set once at the ingress BEB and never touched in transit. BCBs read B-DA, look up B-FIB, forward — no rewrite. The envelope is stamped at the on-ramp, stripped at the exit. Traditional Ethernet rewrites the destination MAC at every hop. Fabric does not.

Breakthrough — Topology vs Service (The Key Gap)

Q: How does IS-IS know which switch hosts which I-SID?

Your synthesis: "Know the roads, know the services. B-FIB = roads, I-SID = services."

Locked answer: IS-IS carries two categories in its LSPs: (1) topology adjacencies → Dijkstra → B-FIB. (2) I-SID service membership (RFC 6329 TLVs) → I-SID membership table. Separate TLV types, same LSP flood. The B-FIB tells you how to reach a switch. The I-SID membership tells you which switch hosts which service.

The Two-Lookup Chain at Ingress BEB

Q: If I have a client on I-SID 100010 and want to send to a laptop on I-SID 100020 — what does IS-IS do?

Locked answer: IS-IS cannot do it — the I-SID boundary is structural L2 isolation. To cross I-SIDs you must go to L3 via the Anycast Gateway SVI → inter-VLAN routing → ACL controls. The ingress lookup chain: (1) I-SID Membership — which BEBs host this service. (2) Service FIB (C-MAC) — which BEB has this specific client (flood-and-learn if unknown). (3) B-FIB — how to reach that BEB.

The Tunnel Synthesis (Your Analogy — Validated)

Your words: "Fabric is a protocol which deploys a MAC-in-MAC tunnel to route data from source to destination with one B-SA and B-DA."

Validated with precision: Fabric is a system of three standards (IS-IS + SPB + PBB). The "tunnel" behaviour is correct — B-SA = entry, B-DA = exit, BCBs = transparent highway, exit decided once at the on-ramp. Distinction: it's L2 encapsulation (MAC header), not IP tunnel (GRE/VXLAN). But the transparency and fixed-endpoint behaviour is identical to a tunnel.

Q — BEB vs BCB in Your Home Lab

Q: Is your single 5320 a BEB, BCB, or both?

Your answer: "BEB and BCB — there are no others on the other side?"

Corrected: BEB only. BCB exists between BEBs — there's no transit node needed when you have one switch. Your single 5320 is simultaneously the ingress BEB and egress BEB — it wraps and unwraps on the same box. In your two-switch lab: both 5320s are BEBs (each has client ports + NNI). BCB would only appear if you added a third switch with no client ports purely for transit.

D4 — Anycast Gateway Deep Dive

Trombone Routing — Eliminated

Without Anycast (VRRP, SW1 = primary): client roams to SW2 but gateway is still on SW1. Every packet crosses NNI twice. With Anycast: SW2 IS the gateway — traffic routes locally, no NNI hop for the gateway lookup.

Anycast MAC Origin

The Anycast MAC is not configured — it is mathematically derived from the I-SID number. Every BEB with vlan i-sid 20 100020 gets the identical MAC automatically. No conflict because the fabric is designed for this — each BEB only answers for clients on its own local ports.

Roaming Flow with Anycast

Client roams SW1 → SW2
Before: gateway on SW1 (VRRP) → trombone every packet
After:  SW2 Anycast Gateway already active → routes locally → zero gap

Cross-I-SID Routing + Provisioning

Scenario — AP on I-SID 100020, Laptop on I-SID 100030

I-SID boundaries are structural L2 isolation — the fabric will not carry traffic between them directly. The BEB is the only crossing point, via L3 routing between the two VLAN SVIs.

AP client (10.0.20.50, I-SID 100020)
    → sends to default gateway 10.0.20.1
    → hits BEB Anycast Gateway SVI for VLAN 20
    → BEB L3 routing: destination 10.0.30.50 → VLAN 30 / I-SID 100030
    → delivers to laptop

Fabric sees two separate flows:
    Flow 1: AP client → BEB        (inside I-SID 100020)
    Flow 2: BEB → laptop           (inside I-SID 100030)
I-SID boundary crossed ONLY inside the BEB routing engine — never in the fabric core.
BEB Wears Two Hats
Ingress BEB for I-SID 100020 → L3 Router (routes between VLAN 20 and VLAN 30 SVIs) → Egress BEB for I-SID 100030. One physical switch, three logical roles simultaneously.

Mixed Mode — VOSS Core + EXOS Edge

Can a campus run both fabric and EXOS switches simultaneously? Yes. VOSS and EXOS coexist via a clean boundary: 802.1Q trunk between the last VOSS BEB and the first EXOS access switch. The fabric terminates at the BEB; EXOS sees a conventional trunk.

LayerTechnologyKnows About Fabric?
VOSS BEB (edge)MAC-in-MAC encap/decapYes — full IS-IS + SPB participant
VOSS BCB (transit)B-DA forward onlyTopology only — not services
EXOS access switch802.1Q trunk to BEBNo — sees normal VLANs only
AP on EXOS portStandard associationNo — treated as ordinary wired client
Trade-off
APs on EXOS ports do not get Fabric Attach auto-provision. Their SSIDs must be mapped to VLANs manually on the EXOS trunk, then the BEB maps VLAN → I-SID at the boundary. FA plug-and-play is a fabric-edge-only feature.
Use Case
Legacy hardware in branch offices keeps running EXOS. New core switches run VOSS. Transition is incremental — swap edge switches one building at a time, moving the fabric boundary outward.

Campus Network Design — No Dedicated Core

A campus of 10 buildings, 20 switches: does fabric need a dedicated core switch? No. IS-IS adapts to whatever physical topology you cable. Every VOSS switch is either a BEB (has client-facing ports) or a BCB (transit-only). The roles emerge from the topology, not from explicit configuration.

The Rule
IS-IS treats all VOSS switches equally. A ring, a star, a partial mesh — same configuration on every switch. IS-IS discovers the topology and computes shortest paths. No "core" designation, no hierarchy to configure.

Auto-Sense + Fabric Attach — Plug-and-Play

Auto-Sense and Fabric Attach together eliminate manual port VLAN configuration on AP-facing ports. The switch listens, classifies the device, and provisions automatically.

How the Switch Tells an AP from a Laptop

DeviceLLDP SignalSwitch Response
AP (e.g. AP3000)Sends LLDP-FA TLVs: device type = WAP Type 1, requested I-SIDs listedAuto-Sense: applies AP profile → FA auto-provisions VLAN/I-SID on that port

The FA Handshake Sequence

AP powers on → boots with EP1 policy already pushed
  ↓
AP sends LLDP-FA TLVs: "WAP Type 1, I need I-SID 100070 (Corp_New)"
  ↓
Switch auto-sense sees FA TLVs → looks up AP profile
  ↓
I-SID 100070 exists on this switch (from SE/EP1 switch policy) → provisions VLAN on this port
  ↓
AP gets DHCP → clients associate to Corp_New SSID → fabric delivers traffic
Plug-and-Play Promise
Fabric does the plumbing. Auto-Sense reads the label on the pipe.
New AP physically plugged in → no port config changes on the switch. The AP declares what it needs via LLDP-FA; the switch delivers it automatically — as long as the I-SID exists on the fabric.
Prerequisite
Auto-sense ports must have auto-sense enable + fa enable. Auto-sense profiles (AP, laptop, phone, unknown) must be defined in EP1 or SE. Without profiles, auto-sense listens but doesn't know what to provision.

AP Policy Push — The Two-Push Rule

After provisioning the switches, a second, separate push to the APs is required. Two independent pushes: one to the switches, one to the APs. Both are necessary; neither is sufficient alone.

PushToolConfiguresWhat happens without it

or
EP1 → Network Policy → Switching		 IS-IS, SPBM, I-SIDs, Anycast Gateway SVIs, DHCP, port roles Fabric doesn't know these I-SIDs exist. APs cannot request what isn't there.
2 — AP Network Policy EP1 → Network Policy → Wireless SSIDs, radio profiles (WMM, DCS, BSS coloring, TWT), SSID → I-SID mapping AP boots and gets an IP, but sends no FA TLVs. Switch auto-sense cannot provision. No wireless clients get service.

Why the AP Needs Its Own Push

The AP needs to know two things before it can participate in the fabric:

  1. Which SSIDs to broadcast — defined in the EP1 Wireless Network Policy
  2. Which I-SID each SSID maps to — the EP1 SSID→I-SID binding tells the AP what to put in its LLDP-FA TLVs

Without push 2, the AP broadcasts no SSIDs (or wrong ones) and sends no FA TLVs. The switch is ready, the fabric is ready — but the AP has nothing to request.

Correct Push Sequence

Step 1: SE  → VOSS Domain → 5320_fabric_se   → Enforce Policy  (defines I-SIDs on fabric)
Step 2: EP1 → Network Policy (Switching)      → 5320_Exos_EP1  → Complete Config Update
Step 3: EP1 → Network Policy (Wireless)       → AP3000_1, AP3000_2 → push  ← DO NOT SKIP
Step 4: Cable NNI between switches
Step 5: Verify:
  show isis neighbors          # adjacency UP?
  show vlan i-sid              # I-SIDs provisioned?
  show fa assignment           # APs got their I-SIDs?
  show ip dhcp-server binding  # clients getting IPs?
Mental Model
Switch policy = "I have I-SID 100070 ready on this fabric."
AP policy = "When you boot, request I-SID 100070 for SSID Corp_New."
Both sides of the conversation must be configured before the FA handshake can happen.
