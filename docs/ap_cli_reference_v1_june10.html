5 · WiFi 6 (802.11ax) Feature Parameters

All of these are read from show interface wifi0 output. The AP3000 supports 802.11ax on both radios. Each feature can be enabled/disabled via XIQ Radio Profile — the AP exposes current state via SSH.

WiFi 6 FeatureDefinitionState / RangeImpact on performance
HE OFDMA DL FLAG Orthogonal Frequency Division Multiple Access — Downlink. AP splits channel into Resource Units (RUs) and simultaneously transmits to multiple clients in a single PPDU. Analogous to 5G downlink scheduling. enabled / disabled +30–40% throughput in dense deployments. Requires clients that support HE OFDMA. capMult_ofdmaDL ×1.35 in simulator.
HE OFDMA UL FLAG OFDMA — Uplink. AP schedules multiple clients to transmit simultaneously in different RUs. More complex than DL — requires AP to send Trigger Frame first. enabled / disabled Reduces uplink airtime congestion. Less common than DL OFDMA in practice.
MU-MIMO FLAG Multi-User MIMO. AP uses spatial steering (beamforming) to transmit to multiple clients simultaneously on separate spatial streams. WiFi 6 supports 8-stream MU-MIMO (vs 4-stream in WiFi 5). enabled / disabled AP3000 = 2×2 so limited MU-MIMO benefit. Real gains on 4×4+ APs. Requires MU-MIMO capable clients.
BSS Color POLLED 1-bit color tag in every 802.11ax frame header. Allows receivers to distinguish between frames from overlapping BSSs. Client that hears a frame with different BSS color → may not defer (spatial reuse). Reduces unnecessary deferrals. Analogous to 5G ICIC. 0 (disabled) or 1–63 Reduces collisions in high-density environments with many APs. Automatically managed by AP.
TWT (Target Wake Time) FLAG AP negotiates a specific wake schedule with each client. Client radios sleep between TWT windows — extends battery life. IoT and mobile devices benefit most. Analogous to 5G eDRX. enabled / disabled Battery life improvement for IoT/mobile. Slight overhead in negotiation. Not useful for latency-sensitive apps.
Tx Beamforming FLAG AP adjusts phase and amplitude per antenna chain to steer signal energy toward the target client. Improves SNR at client → higher MCS → higher throughput. Requires client feedback (CSI sounding). enabled / disabled +2–5 dB SNR improvement per client. Most impactful for edge clients (weak SNR).
A-MPDU FLAG Aggregate MAC Protocol Data Unit. Bundles multiple frames into a single transmission to amortize the overhead of 802.11 MAC headers, SIFS, ACK. Standard since 802.11n. A-MPDU is the primary driver of "MAC efficiency" in the simulator. enabled / disabled Critical for throughput. Disabling drops efficiency dramatically. Should always be enabled.
Short Guard Interval FLAG Guard interval is the silence between OFDM symbols to prevent inter-symbol interference (multipath delay). Short GI = 400 ns (vs 800 ns standard). WiFi 6 HE GI: 0.8/1.6/3.2 µs options. Shorter GI = higher throughput but more multipath sensitivity. enabled / disabled ~11% throughput gain in clean environments. Risk: multipath-heavy environments (warehouse, concrete) may see more errors with short GI.
Dynamic Channel Width FLAG AP can dynamically narrow channel width (e.g. 80→40→20 MHz) based on interference. WLANPros: DISABLE this. Dynamic width breaks roaming — clients cached at 80 MHz try to reassociate on a 40 MHz channel and fail, causing a full de-auth/re-auth cycle. enabled / disabled DISABLE — breaks roaming. Set fixed channel width in design.
Benchmark 11ax POLLED AP3000 internal 802.11ax benchmark score (0–100). Composite internal metric combining HE feature adoption, MCS distribution quality, and frame efficiency. Higher = better WiFi 6 utilization. 0–100 Useful as a quick health indicator. Not standardized across vendors.

9 · When Handoff Doesn't Occur — L2/L3 Signatures

A roaming failure is not always visible from the AP's side as an error — the client stays associated. You have to infer it from the combination of declining PHY metrics and the absence of expected 802.11 management frames in the pcap.

What to look for in PHY (AP polling)

  • snr_db for the stuck client falls below 20 dB but the client never de-associates
  • tx_rate_mbps and rx_rate_mbps for the client drop progressively (MCS degradation)
  • crc_error_pct increases on the radio the sticky client is on
  • station_state stays run — the AP is still serving the client, it just isn't moving

What to look for in L2/L3 pcap

# Filter to see roaming management frames
wlan.fc.type_subtype == 0x000d   # Action frames (includes 802.11k, 802.11v, FT)
wlan.fc.type_subtype == 0x0000   # Association Request (new AP assoc)
wlan.fc.type_subtype == 0x0002   # Reassociation Request (this is what FT looks like)
wlan.fc.type_subtype == 0x000c   # Deauthentication (reason 3 = station left)

Stuck client (no handoff) signatures:

  • No Reassociation Request frames from the client MAC
  • No BSS Transition Management (802.11v) Request/Response exchange
  • No FT Action frames (if 802.11r configured)
  • Increasing retry rate on data frames from/to this client MAC
  • Eventually: Deauthentication reason 8 (client-initiated) or reason 3 (AP-initiated safety-net)

10 · 4-Way Handshake in pcap — L2/L3 Messages & AP Poll Correlation

The 4-Way Handshake is the 802.11i/WPA2 protocol that establishes the Pairwise Transient Key (PTK) between AP and client after successful authentication. Every WiFi connection does this — it's the last step before data flows. You see it in pcap as EAPOL frames. You see its health in AP polling as station_state transitions and CRC spikes.

MessageDirectionContentsWireshark Filter
M1 — ANonce AP → Client EAPOL Key, Authenticator Nonce (ANonce), no MIC. Starts the key derivation. AP sends PMK reference (the PPSK or network PMK is already known by both sides). eapol && wlan.fc.type == 2
M2 — SNonce + MIC Client → AP EAPOL Key, Supplicant Nonce (SNonce), MIC set (proves client has correct PMK). Includes RSNE (cipher suites). If MIC is wrong → AP sends Deauth reason 15 (MIC failure). This is where PPSK verification happens. eapol → look for Key Info flag MIC=1, ACK=0
M3 — GTK AP → Client EAPOL Key, GTK (Group Transient Key) encrypted with derived KEK, Install flag set, MIC set. Provides the broadcast/multicast key. Client must acknowledge within retry window. Key Info: Install=1, MIC=1, ACK=1
M4 — ACK Client → AP EAPOL Key, empty payload, MIC set. Acknowledges M3. After this: PTK is installed on both sides, TK (Temporal Key) encrypts data frames. Station transitions to run. Key Info: MIC=1, ACK=0 (after M3)

When the 4-Way Handshake fails — what you see

# pcap filter for EAPOL frames only
filter 1 l3 protocol 0x888e      # EtherType 0x888E = EAPOL (802.1X)
capture interface wifi0 duration 60 filter and 1

# Or by error type
filter 2 l2 error mic            # MIC failures = M2 had wrong MIC (wrong PSK)
filter 3 l2 error decrypt        # decrypt errors = TK installed but frame undecodable

PHY correlation — what AP polling shows when 4-way fails:

  • M2 fails → client MAC disappears from show station (deauth), reappears seconds later → retry loop
  • If M2 fails due to low SNR (RF caused bit error in EAPOL) → crc_error_pct spike on that radio
  • If M2 fails due to wrong key (wrong PPSK) → CRC will be clean, decrypt error in pcap, deauth reason 15
  • Multiple EAPOL sequences for same MAC within 30s = retry storm — see in show station as rapid state changes
  • _kdebug auth basic + _kdebug dot1x basic — kernel-level auth trace shows exact EAPOL state machine step that failed

11 · PPSK in pcap vs Physical Layer

What PPSK looks like in pcap

At the L2/L3 level, PPSK uses standard WPA2 4-Way Handshake — identical to WPA2-PSK. The difference is invisible to the pcap: each client derives a different PMK from their unique PPSK. The AP verifies M2 using the PMK for that client's specific PPSK, not a shared network key.

# In Wireshark — PPSK looks exactly like WPA2-PSK. You will see:
EAPOL M1 → M2 → M3 → M4   # all four messages present = success
EAPOL M1 → M2              # then deauth reason 15 = wrong PPSK key used
EAPOL M1 only              # timeout = client has wrong passphrase, gave up

PPSK verification flow

# Check PPSK key bindings on AP
show auth private-psk         # → table: client MAC | PPSK | VLAN | user-profile
show auth mac-binding <ssid>  # MAC-locked PPSK entries for this SSID

# When a client fails PPSK auth — debug flow
_debug auth error             # shows "MIC verify fail" or "PMK lookup fail"
_debug wpad wifi all          # WPA daemon — shows full 4-way state machine

13 · Session Recording

The AP CLI does not have a native "log to file" command for interactive sessions. Best approach: wrap your SSH session in a script command on your laptop — everything echoed to your terminal is captured.

# Method 1: script wrapper (RECOMMENDED — captures everything)
# Run this on your laptop BEFORE opening the SSH session
script -a ~/ap_session_$(date +%Y%m%dT%H%M%S).txt
ssh admin@<AP_IP>
# ... all AP output is logged to the .txt file in real time
# To end: Ctrl-D (exits script session, closes log file)

# Method 2: tee — SSH output to both terminal and file simultaneously
ssh admin@<AP_IP> | tee -a ap_session.log
# Note: input (your commands) not captured — only AP responses

# Method 3: AP console debug stream to terminal (then captured by Method 1)
# From INSIDE the AP CLI:
debug console all
debug console timestamp    # adds timestamps to every debug line
# All debug output now streams to your SSH session — captured by script
debug console level info   # reduce verbosity: emergency|alert|critical|error|warning|notification|info|debug

# Method 4: Syslog to remote server (persistent across reboots)
# Configure in XIQ: System → Syslog → Server IP + port 514
# All AP events sent to syslog server continuously
Best practice for diagnostic sessions: Always use script -a before SSH. The -a flag appends to the file (vs overwrite). Name the file with ISO timestamp. After the session: grep 'error\|CRC\|decrypt\|deauth' ap_session_*.txt to quickly find relevant events.
