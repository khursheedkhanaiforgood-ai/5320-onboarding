CRC + Interference Analysis

wifi0 — 47% CRC peak, root cause confirmed

ACSP neighbor scan showed QFiberKK at −24 dBm on channel 11 — same channel as our AP, 1 foot away. This is inbound CoPer-channel interference. The CRC manifests as:

  • Frames arriving at the AP with bit errors — CRC counter increments
  • AP's own TX power is irrelevant — interference is inbound, not outbound
  • Reducing TX power was confirmed ineffective (tried 1 dBm → no change to CRC)
  • Only real fix: channel change (1 or 6 are cleaner; channel 9 is NOT non-overlapping)
Channel 9 is wrong. 2.4 GHz non-overlapping channels are 1, 6, 11 only. Channel 9 overlaps both 6 and 11 — using it creates interference on two channels simultaneously.

The 80 MHz Fix — Full Story

This is a case study in the EP1 ↔ AP config hierarchy.

Timeline

StepActionResult
1CLI: radio profile radio_ng_11ax-5g channel-width 20wifi1 dropped to 20 MHz · Noise floor: −90→−94 dBm (4 dB improvement)
2EP1 policy pushed (unrelated change)EP1 overwrote CLI change — wifi1 stayed at 20 MHz (policy was already 20 MHz)
3User created radio profile 5G_Khursheed_80MHz in EP1 with 80 MHzEP1 pushed profile definition to AP — profile appeared in show radio profile
4EP1 policy deploy failed: "Device update failed"Profile definition pushed but Bind interfaces= None — AP didn't bind it to wifi1
5CLI: interface wifi1 radio profile 5G_Khursheed_80MHzProfile bound to wifi1 · Radio re-initialized · Both clients reconnected at 80 MHz · Tx rate 907–1134 Mbps
Key insight: EP1 is the authoritative config source — CLI changes are temporary and get overwritten on next policy push. The EP1 deploy failure was the root issue. Profile definition was pushed (step 3) but the full policy including the binding failed (step 4). CLI fixed the binding immediately (step 5). EP1 deploy failure still needs investigation (likely SDR/firmware profile conflict).

pcap Transfer Architecture — Discovery

The existing CaptureAgent in capture_agent.py uses SFTP to pull pcap files from the AP. This is broken on IQ Engine — SFTP subsystem is disabled. Today's investigation confirmed the correct architecture:

MethodResultWhy
SFTP pullFails — subsystem request failed on channel 0HiveOS SFTP subsystem disabled
SCP transferFails silently — 0 bytes transferredSCP not supported properly
ssh admin@AP 'cat /tmp/file.pcap'Empty — file not in /tmp/AP stores captures in private partition, path unknown
Remote sniffer (TCP stream)Works — live pcap stream to MacAP streams raw pcap frames over TCP; no file transfer needed

Remote sniffer command

# On AP — start streaming to Mac
exec capture remote-sniffer interface wifi1 host-allowed 192.168.0.x local-port 2003 promiscuous

# On Mac — receive stream
nc 192.168.0.12 2003 > cap_wifi1.pcap

# Or open directly in Wireshark (real-time)
# Capture → Manage Interfaces → Remote → 192.168.0.12:2003
