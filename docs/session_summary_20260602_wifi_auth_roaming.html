§1 — Packet Capture Setup

Two shell aliases live in ~/.zshrc for fast Mac-side captures on en0 (Wi-Fi, confirmed via networksetup -listallhardwareports):

function wcap() { /Applications/Wireshark.app/Contents/MacOS/dumpcap -i en0 -a duration:$1 -w ~/Desktop/$2.pcapng && open ~/Desktop/$2.pcapng; }
# Usage: wcap 30 mycapture  →  captures 30s, saves to Desktop, opens Wireshark

alias wscan="/Applications/Wireshark.app/Contents/MacOS/dumpcap -i en0 -w - | \
  /Applications/Wireshark.app/Contents/MacOS/wireshark -k -i -"
# Usage: wscan  →  live stream directly into Wireshark, no file

Limitation: Both capture at the Ethernet layer — no 802.11 radio headers, RSSI, MCS, or channel info. Monitor mode requires admin/sudo rights (not available on work Mac). For 802.11 frames use the AP remote sniffer or Wireless Diagnostics on a personal Mac.

AP Remote Sniffer (802.11 frames with radiotap)

The AP3000 (IQ Engine) has a built-in remote sniffer. On AP CLI:

exec capture remote-sniffer interface Wifi1 host-allowed 192.168.0.24 local-port 2002 promiscuous
show capture remote-sniffer   # confirm Status: Enabled + connected host

Then on Mac:

/Applications/Wireshark.app/Contents/MacOS/wireshark -k -i TCP@192.168.0.12:2002

Wireless Diagnostics (personal Mac — no sudo)

Open Wireless Diagnostics → Window → Sniffer → pick channel + width → Start. Saves .pcap to /var/tmp/. Captures in monitor mode; Mac disconnects from Wi-Fi during the capture. Must select the right channel:

§2 — 802.11 Open Authentication & Association

Authentication (not real security)

Despite the name, 802.11 Open Authentication is a two-frame formality — no credentials exchanged. Real identity proof happens in EAP or the 4-way handshake.

Client → AP: Authentication Request   (algorithm=Open, seq=1)
AP → Client: Authentication Response  (algorithm=Open, seq=2, status=Success)

Association — capability negotiation

The client announces what it supports; the AP assigns it a logical seat.

Client → AP: Association Request
  ├── SSID name
  ├── Supported rates (MCS, bands)
  ├── RSN IE  (WPA2/WPA3, CCMP, PMF)
  └── HT/VHT/HE capabilities (WiFi 4/5/6)

AP → Client: Association Response
  ├── Status (accept/reject)
  ├── Association ID (AID)  ← client's slot on the AP
  └── AP capabilities confirmed

After Association, the client has a logical connection but no encryption keys. No data can flow securely yet — that happens after the 4-way handshake.

On a roam to a second AP, the client sends a Reassociation Request (not Association). This is how you identify a roam in a pcap — look for the Reassoc frame type, not Assoc.

§3 — The 4-Way Handshake (EAPOL)

The 4-way handshake is mandatory in WPA2 and WPA3 regardless of authentication method. Its job: derive a per-session encryption key (PTK) from the PMK without ever transmitting the key over the air.

AP  → Client: EAPOL Key (Message 1 of 4) — ANonce (AP random number)
Client → AP:  EAPOL Key (Message 2 of 4) — SNonce + MIC
AP  → Client: EAPOL Key (Message 3 of 4) — GTK (encrypted) + MIC
Client → AP:  EAPOL Key (Message 4 of 4) — Ack + MIC

What happens inside each message

MessageWhat happens
M1 — ANonceAP sends its random nonce. Client now has both nonces.
Client derives PTKPTK = PRF(PMK + ANonce + SNonce + AP_MAC + Client_MAC) — computed locally, never sent.
M2 — SNonce + MICClient sends its nonce + a Message Integrity Code proving it knows the PMK.
AP derives PTKAP runs the same formula — both sides now have identical PTK.
M3 — GTK + MICAP sends the Group Temporal Key (for broadcast/multicast), encrypted with PTK. MIC proves AP knows PMK.
M4 — AckClient confirms keys installed. Encryption starts.

Key insight: The PTK is never sent over the air. Both sides independently compute the same key. This is why WPA2 is secure even when the 4-way frames are captured.

§4 — PSK vs EAP (802.1X)

The 4-way handshake always appears. The difference is how the PMK is derived before it:

PSK:
  Auth → Assoc → 4-way handshake (PMK derived from shared password)

EAP-PEAP (802.1X):
  Auth → Assoc → EAP Identity → PEAP/TLS tunnel → EAP Success → 4-way handshake

EAP-TLS (802.1X):
  Auth → Assoc → EAP Identity → mutual TLS (both certs) → EAP Success → 4-way handshake
MethodEAP needed?RADIUS needed?Certs needed?4-way?
PSKNoNoNoAlways
EAP-PEAPYesYesServer onlyAlways
EAP-TLSYesYesBoth sidesAlways

Can a client roam to a different SSID without disconnecting? No. SSID change always requires a full deauth → fresh probe → auth → assoc → 4-way. 802.11r only skips the 4-way when roaming within the same SSID/ESS.

§5 — EAP Deep Dive

EAP (Extensible Authentication Protocol) is a framework, not a single method. It has an outer shell that carries an inner method.

Outer EAP shell (always the same)

AP  → Client: EAP Request/Identity
Client → AP:  EAP Response/Identity  (username)
AP  → Client: EAP Request/<method>
... inner method exchange ...
AP  → Client: EAP Success / Failure

EAP-PEAP — most common enterprise deployment

1. TLS tunnel established using server certificate only
2. Inside the encrypted tunnel:
     Client → RADIUS: MSCHAPv2 username
     Client → RADIUS: MSCHAPv2 password hash
     RADIUS validates against Active Directory
3. EAP Success → PMK derived → 4-way handshake

The AP is a passthrough — it forwards EAP between client and RADIUS (UDP port 1812). The AP never sees the password.

EAP-TLS — high security environments

1. EAP Request/Identity (x3 retransmits visible in pcap)
2. TLS tunnel — server sends cert, client sends cert (mutual)
3. Server issues Certificate Request → client must prove identity with its own cert
4. EAP Success → PMK derived → 4-way handshake

EAP-PEAP vs EAP-TLS decision

EAP-PEAPEAP-TLS
Client cert requiredNoYes
PKI requiredNoYes — every device
CredentialsUsername + passwordCertificate
AD/LDAP integrationNativePossible but complex
Typical useCorporate 802.1X, NPSBanking, government, healthcare

§6 — Roaming & 802.11r Fast Transition

Standard roaming (no 802.11r)

Probe → Auth → Reassoc → full 4-way handshake (new PTK)

802.11r Fast Transition

FT Auth (keys pre-negotiated here) → Reassociation Request/Response → data resumes

No EAPOL on the roam. The FT Auth frames carry the key material. By the time Reassoc completes, keys are already installed.

Proof from wpa2-ft-psk.pcapng

FrameTimeEventAP
5–60.19sAuthenticationAP1 02:00:00:00:00:00
7–80.20sAssociation Request/ResponseAP1
9–120.20sEAPOL 4-way (keys 1→2→3→4)AP1
13–2314–32sData flowingAP1
24–2562.8sFT Auth → AP2 (roam)AP2 02:00:00:00:01:00
26–2762.8sReassociation — no EAPOLAP2
28–3363s+Data continues on AP2AP2

Smoking gun: Frame 26 is a Reassociation Request, not an Association Request. And there is no EAPOL between frame 12 and the end of the capture. That is 802.11r working as designed — the roam took under 20ms.

Mental model — complete picture

PSK:      Auth → Assoc → EAPOL 4-way → data
                                    ↓ roam (802.11r)
                          FT Auth → Reassoc → data (no EAPOL)

EAP-PEAP: Auth → Assoc → EAP/PEAP → EAPOL 4-way → data
                                    ↓ roam (802.11r)
                          FT Auth → Reassoc → data (no EAPOL)

EAP-TLS:  Auth → Assoc → EAP/TLS (mutual certs) → EAPOL 4-way → data
                                    ↓ roam (802.11r)
                          FT Auth → Reassoc → data (no EAPOL)

Useful Wireshark display filters

eapol              # isolate 4-way handshake messages
eap                # isolate EAP identity + method exchange
wlan.fc.type == 0  # management frames only (auth, assoc, deauth)
wlan.fc.type_subtype == 0x0b  # authentication frames
wlan.fc.type_subtype == 0x02  # reassociation requests (roam events)
wlan.fc.type_subtype == 0x0c  # deauthentication
