AP2 → Karl’s VIQ — CAPWAP Debug Journey

The goal was to move AP2 (AH-565780) from the homelab VIQ (VHM-UOZZMDJP) into Karl’s VIQ (VHM-SXJUBHJO) to test RADIUS 802.1X authentication against Karl’s RADIUS server. What looked like a simple re-claim turned into a multi-step redirect debugging session.

CAPWAP State Machine

SULKING → DTLS Handshaking → RUN

An AP in SULKING state means it cannot reach a cloud controller — it retries with exponential backoff. DTLS Handshaking means it found a server and is negotiating the secure tunnel. RUN means it is fully registered and receiving policy.

Key mechanism: The Aerohive/IQ Engine redirector at redirector.aerohive.com maps a serial number to an organization’s cloud VHM ID. Whichever VIQ has claimed that serial number is where the AP redirects on boot — regardless of the AP’s previous state.

Root Causes Diagnosed

AP not appearing on Karl’s VIQ after claim Karl added serial in XIQ Classic — redirector only responds to EP1 claims Karl re-adds serial in EP1 (extremeplatformone.com), not XIQ Classic

XIQ Classic vs EP1 distinction: These are two separate systems. XIQ Classic (extremecloudiq.com) and Extreme Platform One (extremeplatformone.com) maintain separate device registries. The CAPWAP redirector only follows EP1 claims. Adding a device in XIQ Classic has no effect on where the AP points.

The debug output confirmed the AP was reaching Karl’s RADIUS server and receiving an Access-Reject — the server responded but refused the credentials because the test user account was not enrolled in Karl’s RADIUS database. This is a credential management task, not a network configuration issue. Deferred to after PTO.

Tagged vs Untagged VLANs — The Complete Mental Model

This came up from Karl’s client requirement: “no VLAN tagging on the AP side.” Understanding exactly what that means — and what you lose — required working through the full data path from wireless client to switch.

Who Tags Frames?

Wireless clients (MacBooks, iPhones) never tag Ethernet frames with 802.1Q VLAN IDs. They send plain untagged Ethernet. The AP is the entity that adds (or strips) VLAN tags before forwarding traffic to the wired switch port.

EntityDoes it tag?What it does
Wireless client (MacBook, iPhone) Never Sends 802.11 frames to AP; AP handles the rest
AP (IQ Engine) Yes — when configured for trunk Maps each SSID to a VLAN; adds 802.1Q tag before sending to switch
Switch port (access/untagged) No tagging added Accepts untagged frames; assigns to native VLAN
Switch port (trunk/tagged) Expects tags from AP Routes each tagged frame to correct VLAN

Untagged Port Scenario

When the AP’s switch port is configured as an access (untagged) port, all traffic from all SSIDs lands on the native VLAN — typically VLAN 1. There is no VLAN separation at any layer below L3. Staff and Guest traffic are indistinguishable at the switch.

ScenarioStaff SSIDGuest SSIDSwitch sees
Untagged / Access port Untagged → VLAN 1 Untagged → VLAN 1 Everything on VLAN 1 — no separation
Tagged / Trunk port Tag VLAN 20 Tag VLAN 10 VLAN 10 and VLAN 20 separate — full isolation possible

Why You Cannot Isolate SSIDs Without Tags

Three isolation mechanisms that seem like options but do not solve the untagged problem:

Inter-station blocking

Only blocks clients within the same VAP/SSID from communicating with each other. A Staff client and a Guest client on different SSIDs are on different VAPs — inter-station blocking does not apply across SSIDs. And even if it did, they are still on the same VLAN 1 subnet, so the restriction is only at the AP data-path level, not enforced by the switch.

EP1 Firewall

EP1’s policy firewall operates at the L3 routing boundary — it controls what routed traffic can flow between different subnets/VLANs. When all clients are on the same VLAN 1, all communication is pure L2 switching within one broadcast domain. There is no L3 routing boundary for the firewall to intercept.

Switch-level VLAN filtering

The switch would need to know which client belongs to which VLAN — but without tags, all frames arrive identical. The switch has no basis for filtering.

Bottom line on no-tagging: If a client requires untagged AP ports and runs multiple SSIDs, accept that all users share the same VLAN and subnet. The only per-SSID differentiation available is QoS class and SSID authentication type — not network isolation. Scope this clearly with the client before deployment.

What Tagged Frames Look Like in Wireshark

A tagged (802.1Q) frame has an extra 4-byte header inserted between the source MAC and the EtherType:

Source MAC  →  Destination MAC  →  [802.1Q: VLAN ID=20]  →  EtherType  →  Payload
Wireshark observationWhat it means
vlan filter returns results; Protocol = 802.1Q Switch port is trunk — AP is tagging
vlan filter returns nothing Switch port is access — no tags present
Frame details show VLAN ID: 10 That specific frame belongs to VLAN 10
Laptop on switch port gets APIPA (169.254.x.x) Trunk port — laptop’s untagged frames rejected; smoking-gun for trunk
Laptop gets real DHCP IP Access port — native VLAN is serving DHCP

Live Client: Sacramento Remote Passive Capture Strategy

The Problem

A live client site in Sacramento has old APs (last accessed 2019, no SSH capability, lost admin password, no XIQ or radio policy history) connected to HPE switches that are also inaccessible remotely. The task is to understand the existing network configuration well enough to rebuild and redeploy policy — before touching a single device.

Two-phase approach: Phase 1 = passive observation (remote, no changes, no on-site visit). Phase 2 = factory reset + EP1 claim + policy build (requires hands-on, potentially on-site for the AP reset).

Phase 1 — What to Tell the Sacramento Client to Run

Step 1: Beacon scan (what the AP is advertising)

Windows:

netsh wlan show networks mode=bssid

macOS: Hold Option key, click Wi-Fi menu icon in menu bar.

From this output you get: SSID name(s), authentication type (WPA2-Personal / WPA2-Enterprise / Open), encryption, BSSID (AP MAC address → OUI → vendor and AP generation).

Step 2: Plug laptop into the switch port the AP uses

Ask the client to temporarily unplug the AP and plug in a laptop. Then run:

# Windows
ipconfig /all

# macOS
ipconfig getifaddr en0
networksetup -getinfo "Wi-Fi"
ResultInterpretation
Gets real DHCP IP (e.g. 192.168.1.x) Access port — native VLAN, DHCP is live on that VLAN
Gets APIPA (169.254.x.x) Trunk port — laptop’s untagged frames aren’t accepted; AP was doing VLAN tagging
No IP, no APIPA Port may be shut down or require specific VLAN tag

Step 3: Wireshark capture on the switch port (adds precision)

Client installs Wireshark (free), captures 30 seconds on the Ethernet port, sends you the .pcapng file. Apply filter:

vlan
  • 802.1Q frames visible, VLAN IDs shown → trunk port; VLAN IDs tell you exactly what to configure in the new policy
  • No 802.1Q frames → access port; single VLAN, check ipconfig for subnet

Three Remote Options (Ranked by Effort)

OptionWhat client doesWhat you get
1 — ipconfig only Unplug AP, plug laptop, run ipconfig /all, send screenshot 80% — native VLAN subnet, DHCP server, gateway. APIPA = trunk confirmation.
2 — Screen share Share screen via Zoom/Teams while you talk them through Wireshark 95% — you read Wireshark live; see VLAN IDs in real time
3 — Client runs Wireshark, sends pcap Install Wireshark, capture 30s, email .pcapng to you 100% — full frame-level truth; you analyze locally at your own pace

What You Need Back from Them

  1. Screenshot of netsh wlan show networks mode=bssid or Option+Wi-Fi menu output
  2. Screenshot of ipconfig /all from the switch port (with AP unplugged)
  3. Wireshark pcapng file (30-second capture, no filter applied, from switch port)

With these three artifacts you can determine: number of SSIDs and encryption type (drives RADIUS vs PSK decision), native VLAN and subnet (drives SW1/HPE switch policy), and tagged vs untagged (drives whether AP template needs VLAN bindings or not).

Phase 2 — After You Have the Data

Factory reset the old AP (console cable required — this may need an on-site visit), claim serial in EP1, build an AP policy matching what the HPE switch expects (access or trunk, correct VLAN IDs), push via EP1. The config becomes a fill-in-the-blank exercise once Phase 1 data is in hand.

On-site trigger: If the AP truly has no console access and no SSH, the only remaining option is a physical button reset (paperclip reset hole on most Aerohive APs). That requires someone physically on site.
