802.1X VLAN Assignment
Silently Fails in Production

AP: AH-AP3000 (00:E6:0E:55:66:80)  ·  Switch: EN_5320 (VOSS/FabricEngine)  ·  Auth: EAP-PEAP/MSCHAPv2 via NPS  ·  Date: 2026-08-07

Expected Behaviour

  • User authenticates via 802.1X
  • NPS returns RADIUS Accept + VLAN 5 attributes
  • EP1 classifies user → Staff policy
  • AP tags eth0 uplink frames: 802.1Q VLAN 5
  • Client receives DHCP on Staff VLAN 5

  • Client falls to native VLAN 1

Two Compounding Issues

  • Issue A (switch) — EN_5320 AP uplink port not configured to carry VLAN 5 as tagged. Switch silently drops 802.1Q VLAN 5 frames.
  • Issue B (NPS) — RADIUS attributes from NPS are malformed: wrong Tunnel-Type, multiple Tunnel-Private-Group-Id values, Filter-Id mismatch. EP1 "Radius Attribute" classification rule does not fire reliably.
  • This deck — forensic proof for Issue A via 5 captured pcap files.
Slide 02 / 03  ·  Hypothesis & Test Design

Designing a Controlled Experiment

Khursheed Khan — verbatim hypothesis (2026-08-07)

"The likely cause of the problem is untagged VLANs on the Fabric_Switch_Port."

Decoding the EP1 Classification Methods

"Radius → in EP1 I tag the Radius_Attribute. TVG → In EP1 I tag the third of the three attributes returning from NPS (5). Radius does not work… I know it. But TVG does."

The Falsifiability Test — verbatim

"TVG → 5, then have the user get dhcp through VLAN1_default, then 'try to push it onto VLAN5'. So, if you see .1Q with VLAN5 uplink on eth0 from AP, then my hypothesis holds true, EP1 rightsly configures AP with policy but Fabric_Switch cannot take tagged_VLAN5 and is therefore dropping."

EP1 Classification: Two Methods Tested

  • RADIUS — EP1 rule matches on RADIUS Attribute directly (Filter-Id / Tunnel-* as returned by NPS).
    → Does not fire. NPS attributes malformed. No VLAN tag applied.
  • TVG (Tunnel-Private-Group-Id) — EP1 rule matches on the 3rd tunnel attribute returned by NPS: Tunnel-Private-Group-Id = 5.
    → FIRES correctly. AP tags eth0 with 802.1Q VLAN per policy.

Test Protocol

  • Step 1 — Connect client with TVG5 rule active; let EP1 assign VLAN policy
  • Step 2 — Capture AP eth0 uplink simultaneously
  • Step 3 — Observe whether 802.1Q VLAN 5 tag appears on wire
  • Step 4 — If tagged frames present but DHCP fails → switch drops them
  • Control — Same test without TVG: frames untagged, DHCP succeeds on VLAN 1

Prediction: IF Hypothesis True

TVG5 fires → AP tags eth0 with VLAN 5 → 802.1Q frames appear on wire → DHCP Discovers sent tagged → zero DHCP Offers return → switch drops.

Result After Test

VLAN5_No_DHCP pcap: 169 frames tagged VLAN 5 on eth0. 22 DHCP requests all tagged VLAN 5. Zero DHCP Offers returned. Prediction confirmed.

Control Result

VLAN1 pcap: zero tagged frames. DHCP Offer received. Client gets 10.153.4.11. Proves AP uplink itself is healthy — problem is VLAN-specific.

What a student should notice:
(1) RADIUS handshake (frames 7–~50) is untagged — AP management traffic always rides native VLAN. That is correct and expected.
(2) The moment DHCP begins (frame 76+), frames are tagged VLAN 5. This proves EP1 successfully pushed the VLAN 5 policy to the AP after authentication completed.
(3) Every DHCP frame has yiaddr = 0.0.0.0 — meaning only client-originated Discovers/Requests are present. There is not a single DHCP Offer in this entire 88-second capture.
(4) The silence after each Discover is the switch dropping the tagged frame. The switch has no VLAN 5 in its trunk allowed list for this port, so it discards the frame before it can reach the DHCP server.
(5) In Wireshark: filter with vlan.id == 5 to isolate these frames. Apply dhcp on top to see the unanswered Discovers.

Appendix C  ·  Student Reference — How to Read This in Wireshark

Diagnostic Framework

Wireshark Filters — Cheat Sheet

  • vlan — show all 802.1Q tagged frames
  • vlan.id == 5 — isolate VLAN 5 traffic
  • dhcp — show all DHCP messages
  • dhcp && vlan — DHCP on a tagged VLAN
  • bootp.option.dhcp == 2 — DHCP Offers only
  • bootp.option.dhcp == 1 — DHCP Discovers only
  • radius — RADIUS authentication traffic
  • !vlan && dhcp — DHCP on untagged/native

What Each File Proves

  • VLAN5_No_DHCP — EP1→AP signaling works; switch is the break
  • VLAN1 — AP uplink, cable, and DHCP server all healthy
  • Radius5_VLAN6 — "Radius Attribute" EP1 method is broken
  • TVG5_VLAN6 — Switch drops ALL tagged VLANs, not just VLAN 5
  • TVG5_VLAN1-Staff — Staff identity confirmed; VLAN enforcement fails

Pattern: Switch Drops

Tagged DHCP Discovers present. yiaddr = 0.0.0.0 on every frame. Zero Offers in entire capture. Client retries indefinitely.

Files 1, 4

Pattern: Working

Zero tagged frames. DHCP Discover → Offer sequence visible. yiaddr returns non-zero IP. Client associated and routed.

Files 2, 3, 5

Pattern: Rule Not Firing

RADIUS Accept visible. Zero tagged frames post-auth. Client falls to native VLAN 1. Staff user on wrong VLAN — no error shown.

Files 3, 5

The Decision Tree (for any 802.1X VLAN failure)

  1. Open eth0 pcap. Does vlan filter return any frames post-auth?
    No → EP1/AP never received or acted on VLAN attribute. Check EP1 classification rule + NPS attributes.
    Yes → proceed.
  2. Run dhcp && vlan. Are there Discovers?
    Yes, but no Offers → AP is tagging correctly. Switch port is the problem. Check trunk allowed VLANs on AP uplink port.
    No DHCP at all → client never got past auth. Check EAP sequence.
  3. Run bootp.option.dhcp == 2 (Offers). Is yiaddr the expected VLAN pool?
    Wrong subnet → DHCP server wrong, or client landed on wrong VLAN despite tagging.
    Right subnet → success — verify end-to-end.
📌
Key Lesson Wireshark on the AP uplink (eth0) is the most powerful single diagnostic tool for 802.1X VLAN assignment failures. It sits exactly at the boundary between the wireless/EP1 domain (what the AP was told to do) and the wired/switch domain (whether the switch accepted it). A tagged Discover with no Offer is unambiguous: the AP did its job; the switch did not.
