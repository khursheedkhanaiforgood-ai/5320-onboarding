Root Cause (switch port)

Lab context: AP3000 (00:E6:0E:55:66:80) authenticates wireless clients via 802.1X EAP-PEAP/MSCHAPv2 against a Windows NPS server. On successful authentication, EP1 (Extreme Platform One) is supposed to classify the user into the Staff policy and instruct the AP to tag client traffic with VLAN 5 on its wired uplink (eth0). The AP connects to an EN_5320 running VOSS/FabricEngine.

Expected chain

  • Client authenticates → NPS returns RADIUS Access-Accept with VLAN 5 attributes
  • EP1 classifies user into Staff policy
  • AP tags eth0 uplink frames with 802.1Q VLAN 5
  • Switch forwards tagged frame into VLAN 5 — client gets DHCP on Staff subnet

What actually happens

  • Client authenticates ✓
  • RADIUS Access-Accept arrives ✓
  • When EP1 classification fires: AP tags eth0 with VLAN 5 ✓ — but switch drops the frame
  • When EP1 classification does not fire: frames go out untagged, client falls to native VLAN 1
  • In both cases: Staff user gets no IP on VLAN 5. No error is shown anywhere.

Two compounding issues Issue A (switch) — root cause proven by pcap: EN_5320 AP uplink port is not configured to carry VLAN 5 as tagged. It silently drops every 802.1Q VLAN 5 frame it receives from the AP.

Issue B (NPS) — secondary: NPS is sending wrong RADIUS attributes — Tunnel-Type = GRE (should be VLAN/13), Tunnel-Medium-Type = IPv4 (should be 802/6), and multiple conflicting Tunnel-Private-Group-Id values. This prevents the EP1 "Radius Attribute" classification rule from firing reliably.

Slide 2 of 3  ·  Hypothesis & Test Design

Designing a Controlled Experiment

Khursheed Khan — verbatim hypothesis (2026-08-07)

"The likely cause of the problem is untagged VLANs on the Fabric_Switch_Port."

Decoding the two EP1 classification methods tested

"Radius → in EP1 I tag the Radius_Attribute. TVG → In EP1 I tag the third of the three attributes returning from NPS (5). Radius does not work… I know it. But TVG does."

The falsifiability test — verbatim

"TVG → 5, then have the user get dhcp through VLAN1_default, then 'try to push it onto VLAN5'. So, if you see .1Q with VLAN5 uplink on eth0 from AP, then my hypothesis holds true, EP1 rightsly configures AP with policy but Fabric_Switch cannot take tagged_VLAN5 and is therefore dropping."

The two EP1 methods

MethodEP1 Rule Matches OnNPS AttributeResult
Radius RADIUS Attribute directly (Filter-Id / Tunnel-* as returned by NPS) Filter-Id or Tunnel-Type/Medium/Group-Id Does not fire — NPS attributes malformed
TVG Tunnel-Private-Group-Id (attr 81) = 5 Tunnel-Private-Group-Id = 5 Fires correctly — AP tags eth0 with assigned VLAN

Test protocol

  1. Activate TVG5 classification rule in EP1 (match on Tunnel-Private-Group-Id = 5)
  2. Connect client — EP1 assigns VLAN policy, AP tags eth0 uplink
  3. Capture eth0 simultaneously with AP packet capture tool
  4. Observe: does 802.1Q VLAN 5 tag appear on the wire?
  5. Control: same test without TVG rule — frames untagged, DHCP should succeed on VLAN 1

Root cause confirmed Files 1 and 4 are the smoking guns. TVG fires, EP1 correctly instructs the AP, the AP tags eth0 with 802.1Q VLAN 5 (or 6). The switch receives those tagged frames — and returns nothing. Not a single DHCP Offer in either capture. EN_5320 AP uplink port does not have VLAN 5 or VLAN 6 in its trunk allowed list and silently discards every tagged frame for those VLANs.
Fix required — single action on EN_5320 Add VLAN 5 (Staff) as a tagged member on the AP uplink port. The entire EP1 → AP → RADIUS authentication chain is working correctly. The only break is the VOSS switch port configuration. Pending Karl's console password.
Secondary fix — NPS RADIUS attributes Set Tunnel-Type = VLAN (13), Tunnel-Medium-Type = 802 (6), and use a single Tunnel-Private-Group-Id value. Fix before retiring the TVG workaround. The "Radius Attribute" EP1 method will not fire until NPS sends well-formed RFC 3580 attributes.

Student annotation (1) RADIUS handshake (frames 7 onward) is untagged. AP management traffic always rides the native VLAN. This is correct and expected — do not mistake it for a failure.

(2) From frame 76, DHCP frames carry an 802.1Q VLAN 5 tag. This proves EP1 successfully pushed the VLAN 5 policy to the AP after authentication completed.

(3) Every DHCP frame shows yiaddr = 0.0.0.0 — meaning only client-originated Discovers/Requests are present. There is not a single DHCP Offer in the entire 88-second capture. The switch received the tagged Discover and dropped it before it could reach the DHCP server.

(4) Wireshark filter to reproduce: vlan.id == 5 then overlay dhcp — you will see only unanswered Discovers, confirming the switch is the break point.

Three observable patterns

PatternWire evidenceRoot cause
Switch drops Tagged DHCP Discovers. yiaddr = 0.0.0.0 on every frame. Zero Offers. Client retries indefinitely. Switch port not carrying the VLAN as tagged.
Working Zero tagged frames. Discover → Offer visible. yiaddr = non-zero IP. Native VLAN / untagged traffic flows normally.
Rule not firing RADIUS Accept visible. Zero tagged frames post-auth. Client on VLAN 1. No error. EP1 classification rule did not match NPS attributes.

Decision tree for any 802.1X VLAN failure

Step 1 — Open eth0 pcap. Apply filter: vlan
No tagged frames after auth → EP1 or AP never received or acted on the VLAN attribute. Check the EP1 classification rule and the NPS RADIUS attribute values.
Tagged frames present → proceed to Step 2.
Step 2 — Apply filter: dhcp && vlan
Tagged Discovers but zero Offers → AP is tagging correctly. The switch port is the problem. Check the trunk allowed VLAN list on the AP uplink port.
Tagged Offers present → proceed to Step 3.
Step 3 — Apply filter: bootp.option.dhcp == 2. Check yiaddr.
Wrong subnet → DHCP server scope or VLAN mismatch. Verify DHCP pool is bound to the correct VLAN interface on the switch.
Correct subnet → client has an IP. Verify end-to-end connectivity.
Key lesson The AP eth0 uplink capture is the single most powerful diagnostic for 802.1X VLAN assignment failures. It sits exactly at the boundary between the wireless/EP1 domain (what the AP was instructed to do) and the wired/switch domain (whether the switch accepted it). A tagged DHCP Discover with no Offer is unambiguous: the AP did its job correctly — the switch did not.
