Pagination & Filtering on IQ Engine

terminal length is Cisco IOS syntax — it returns unknown keyword or invalid input on IQ Engine. Do not use it.

Alternatives

AH-556680# — filtering & scoping
show log buffered 100Last 100 lines of log buffer
show log bufferedFull log buffer (may scroll)
show running-config | i vlan| i = case-insensitive grep (IQ Engine's filter pipe)
show running-config | i ssidFilter any keyword from running config
The | i pipe is IQ Engine's equivalent of grep -i. It works on any show command output. Use it to scope long configs instead of scrolling.

Practical workaround for long outputs: enable session logging in your terminal emulator (SecureCRT, iTerm2) before running the command, then scroll the buffer after.

_debug vs _kdebug

_debug_kdebug
LayerUserspace daemonKernel / radio driver
Targetsauth, dhcp, roaming, amrp802.11 frame events, key exchange, association state
VerbosityModerateVery high — can flood console
Default outputLive to consoleLive to console
Use caseAuth failures, DHCP, roamingFrame-level, MIC failures, TK desync, retry storms
Key insight: Debug detail does not exist until you turn the flag on. The AP is not silently buffering this data in the background — you must be watching when the event occurs.

Workflow

  1. Clean slate: no _debug all  /  no _kdebug wifi0 all
  2. Start debug: _debug auth all or _kdebug wifi0 mgmt
  3. Trigger the event (client connects, roams, fails auth)
  4. Stop: no _debug all
  5. Review: show log buffered 200

Save to file (survives until reboot)

_debug auth all logfile /tmp/auth_debug.log
show file /tmp/auth_debug.log
/tmp is RAM only — lost on reboot. Pull the file before power cycling.
Prefer scoped flags: _kdebug wifi0 mgmt (management frames only) over _kdebug wifi0 all on a busy AP. The all flag can produce thousands of lines per second.

Packet Capture & ADSP Blocker

Correct capture syntax (IQ Engine)

# Step 1 — set save file
capture save interface wifi1 /tmp/test_capture.pcap

# Step 2 — start capture
capture interface wifi1 duration 30

# Step 3 — verify file
show file /tmp/test_capture.pcap

Capture options available

capture interface wifi1 [option]
count <n>Capture n frames then stop
duration <seconds>Capture for n seconds
filter <expression>BPF-style frame filter
promiscuousEnable promiscuous mode during capture
size <bytes>Max saved file size
ADSP Blocker: Both wifi0 and wifi1 return "Packet capture cannot be set as ADSP sensor mode is enabled on this interface". ADSP (AirDefense Sensor Protocol) uses the radio for continuous WIDS/WIPS scanning — this is architecturally incompatible with packet capture on the same radio. Fix: disable ADSP in EP1 → Radio Profile → WIDS settings → push config → then capture. Re-enable ADSP when done.

EP1 Reverse Tunnel SSH

From a hotel network, direct SSH to 192.168.0.12 times out — the hotel router has no route to your home's private subnet. EP1 solves this transparently.

ScenarioPathWorks?
Home on QF_ModemSame subnet → direct SSH port 22✓ Always
Hotel WiFi → directDifferent network, no route to 192.168.0.0/24✗ Timeout
Hotel WiFi → EP1EP1 cloud port (e.g. 3.145.235.126:20197) → IQAgent tunnel → AP SSH✓ Works
Anywhere with VPN homeEncrypted tunnel back to home subnet✓ Works

How the EP1 tunnel works

The AP makes a persistent outbound connection to EP1's cloud (IQAgent/CAPWAP tunnel). When you click SSH in EP1, it allocates a temporary ephemeral port on its cloud infrastructure and bridges it back through that existing tunnel. The AP never needs an inbound port open — it works through any NAT or firewall. The port closes when you end the EP1 session.

This is the same NAT-traversal principle as the Tailscale VPN we're building — the device calls home, not the other way around.

VoIP Basic Rate + Stickiness

Customer issue: WiFi calling drops on 5 GHz. They asked about changing basic data rates from 6 → 12 → 24 Mbps.

Why basic rate affects stickiness

Beacons are always transmitted at the lowest basic (mandatory) rate. A client stays associated as long as it can decode beacons — so the basic rate sets the effective cell edge.

Basic RateBeacon thresholdClient disconnects atStickiness
6 Mbps~−82 dBm−82 dBmVery sticky
12 Mbps~−79 dBm−79 dBmModerate
24 Mbps~−74 dBm−74 dBmLeast sticky
VoIP minimum RSSI = −67 dBm. At 6 Mbps basic rate, a client at −80 dBm is still "connected" — 13 dB below the VoIP quality floor. The call is failing and the client will not roam.

Coverage shrinkage formula

Each doubling of basic rate costs exactly 3 dB of coverage at the cell edge:

ΔdB = 10 · log₁₀(new_rate / old_rate)

6 → 12 Mbps : 10·log(2) = 3.01 dB
12 → 24 Mbps : 10·log(2) = 3.01 dB
6 → 24 Mbps : 10·log(4) = 6.02 dB
Path loss exponentEnvironment3 dB → range shrinkArea shrink
n = 2Free space / outdoors~29%~50%
n = 3Typical indoor~21%~38%
n = 4Dense indoor / obstructed~16%~29%
Recommendation: Start with 12 Mbps basic rate on 5 GHz for VoIP profiles — 3 dB tighter cell, meaningfully less sticky, minimal coverage impact if AP spacing is adequate. 24 Mbps only for very dense deployments (AP spacing ≤15m).

Stationary Call Drops — Diagnosis

Customer confirmed drops occur while stationary — not during roaming. This eliminates stickiness as the root cause entirely. The call degrades and dies while the client stays associated to the same AP.

Suspects — ranked by likelihood

SuspectMechanismKey diagnostic question
GTK rotationKey-state desync causes ~2–4s decrypt failure windowAre drops rhythmic / periodic?
DTIM / power saveVoIP packets buffered until DTIM beacon → jitter spikeIs phone in power save mode? What is DTIM interval?
Marginal RSSIClient at −72 to −75 dBm — any spike crosses VoIP floorWhat is RSSI at time of drop?
High channel utilizationBeacon overhead at low basic rate + CCI saturates airtimeWhat is CU% on that AP?
WMM / QoS offVoIP (AC_VO) competes with best-effort trafficIs WMM enabled on the SSID?
Key diagnostic: "Are the drops happening at regular intervals — like every 2–3 minutes?"
Rhythmic = GTK rotation or DTIM. Random = interference / SNR / channel utilization.

Home Lab VPN — Setup Guide

Total time: ~20 minutes. After setup: ssh admin@192.168.0.12 works from anywhere.

Step 1 — Flash SD card (10 min)

  1. Download Raspberry Pi Imager: raspberrypi.com/software
  2. Insert microSD into Mac via adapter
  3. Select OS: Raspberry Pi OS Lite (64-bit) — no desktop needed
  4. Click gear icon ⚙ → enable SSH → set username: pi → set password → set hostname: lab-pi
  5. Click Write → wait → eject

Step 2 — First boot (5 min)

  1. Insert SD into Pi → plug ethernet into QF_Modem → plug USB-C power
  2. Wait 60 seconds for boot
  3. From MacBook: ssh pi@lab-pi.local (or find IP in QF_Modem DHCP table)
  4. Run: sudo apt update && sudo apt upgrade -y

Step 3 — Install Tailscale (2 min)

curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --advertise-routes=192.168.0.0/24 --accept-routes

Click the auth URL in the output → sign in with your Google account.

Step 4 — Approve subnet route (1 min)

  1. Go to login.tailscale.com → Machines → lab-pi
  2. Click "…" → Edit route settings → enable 192.168.0.0/24
  3. Click "…" → Disable key expiry (so Pi stays connected without periodic re-auth)

Step 5 — Laptop setup (2 min)

  1. Download Tailscale app: tailscale.com/download
  2. Sign in with same Google account
  3. Toggle on

Step 6 — Test from any network

ping 192.168.0.12        # confirm routing
ssh admin@192.168.0.12   # AP — works from hotel, coffee shop, anywhere
