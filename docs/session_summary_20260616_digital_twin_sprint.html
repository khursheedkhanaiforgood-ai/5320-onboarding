Physics Review — NotebookLLM Session Critique

Reviewed a physics study session on frequency vs. propagation distance. Three errors identified in the explanation:

Error 1 — Symbol Confusion: μ vs λ

Used μ (mu) as the wavelength symbol. Correct symbol is λ (lambda). The relation is c = λν (speed of light = wavelength × frequency). μ is micro- prefix (10&sup6;) or mean in statistics — not a wave variable.

Error 2 — Rayleigh Scattering vs Rayleigh Fading

These are two distinct phenomena that share a name — a common conflation:

TermWhat It IsDomain
Rayleigh ScatteringPhysical process: particles much smaller than wavelength scatter light proportional to 1/λ&sup4; (explains blue sky at visible light, negligible in WiFi bands)Atmospheric optics / physics
Rayleigh FadingStatistical model: received signal amplitude follows Rayleigh distribution when there is no dominant LoS path (many small multipath components)Wireless communications / 802.11

Error 3 — Wave Diffraction Explained as Particle Behavior

Low-frequency waves bending around corners is wave diffraction, not a particle phenomenon. The correct explanation: diffraction angle θ ≈ λ/d. Larger λ (lower frequency) → more diffraction → bends around obstacles. This is a fundamental wave property (Huygens’ principle), not a particle-speed effect.

Key RF propagation formulas (verified):
FSPL = (4πdν/c)² — Free-space path loss; geometric spreading + antenna aperture effect, NOT air absorption
Ae = λ²/4π — Antenna effective aperture; smaller at higher frequency = less intercepted power
TC = (9/16π) · (c/v·f) — Coherence time; at 5 GHz, walking pace 1 m/s → TC ≈ 10.7 ms

ns3-Sionna Paper Deep Dive

Architecture

ns-3 (C++ event-driven packet simulator) and Sionna RT (Python GPU ray tracer, TensorFlow + Mitsuba 3) are separate processes connected via ZeroMQ + protobuf IPC. ns-3 acts as the ZMQ client; Sionna Python server responds with CIR (channel impulse response) on demand. The key extension: a custom C++ PropagationLossModel subclass in ns-3 that calls out to Sionna instead of using a static log-normal model.

The Core Problem ns3-Sionna Solves

Standard ns-3 channel models are spatially inconsistent (path loss is a random draw at simulation start, fixed forever) and geometry-blind (no walls, no reflections). Sionna RT computes physically-accurate CIRs from a 3D scene, giving spatially-consistent, position-dependent channels that update as nodes move.

Four Performance Optimizations

OptimizationHowEffect
Channel ReciprocityA→B CIR = B→A CIR (reuse one computation)2× reduction in Sionna calls
Coherence Time CachingCache CIR for TC ms; reuse if node hasn’t moved past coherence distanceCache hit rate 95–99% at scale
Far-Receiver PruningSkip Sionna call for pairs beyond a distance threshold (use path loss only)Eliminates distant pairs entirely
Predictive P2MP BatchingPre-compute CIRs for nearby APs before client arrives (batch GPU call)14.25× speedup on Tesla V100 for large batches

The GPU Paradox (Table I Results)

RTX 3060 is 3.5–6.5× SLOWER than Ryzen 7 CPU for single P2P link computation. GPU only wins for large batches (R ≥ ~50 receivers). Implication for our 1 AP + 1 client test: CPU mode on MacBook is not just a fallback — it is the correct choice for this geometry.

Performance Overhead vs Pure ns-3

  • Stationary nodes: 3.6–73× overhead (cache hits high once warmed)
  • Low-mobility (pedestrian): 1,400× overhead
  • High-mobility (vehicular): 6,200× overhead
  • At scale with caching: cache hit rate 95–99% → overhead shrinks toward the stationary case
Why this matters for our sprint: 1 AP + 1 static MacBook = 1 link trajectory, computed once, cached forever. The stationary case (3.6× overhead) runs in real time on MacBook CPU. This is the correct starting point.

Validation

Free-space ns3-Sionna CIR matches ns-3 FriisPropagationLossModel exactly — validates the physics integration. Confirmed in Figure 3 of the paper.

MacBook Constraint & Docker Solution

Apple Silicon = Metal architecture, NOT CUDA. Sionna RT falls back to LLVM/Dr.JIT CPU mode automatically when no CUDA device is present. The Docker image FROM tensorflow/tensorflow:2.16.1-gpu runs on MacBook CPU under Rosetta (amd64 emulation). The same container image gets --gpus all on a cloud/DGX instance — no code change required. The platform flag --platform=linux/amd64 is required on Apple Silicon.

Omniverse Clarification

Omniverse USD Composer is a 3D visual editor for building room geometry. It exports to Mitsuba XML (or OpenUSD/Collada). Sionna reads that XML file. Omniverse does NOT run during simulation — it is an offline scene-authoring step. For Phase 0–3, Omniverse is bypassed: static_office.xml is hand-written.
