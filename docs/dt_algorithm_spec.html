DigitalTwinEngine — Algorithm Specification

v1.0 APPROVED    Authored: 2026-06-09  ·  AP Platform: AP3000 HiveOS (WiFi 6)  ·  Scope: Sprint 2b–Sprint 4  ·  Audit reference: docs/dt_algorithm_spec.html
Purpose. This document is the authoritative algorithm specification for the DigitalTwinEngine calibration loop. It serves three roles simultaneously: (1) audit record for any third-party review of the optimization methodology, (2) regression test oracle — every Sprint 3 unit test must produce outputs consistent with the equations here, and (3) implementation contract — Sprint 3 code is written against this spec, not the other way around.

§1 — System Overview

The DigitalTwinEngine operates three concurrent planes:

PlaneFunctionState Machine
Data Plane AP3000 → SSH → APCollectorAgent → SQLite + Dash. What is happening on the radio. Running continuously at POLL_INTERVAL (default 15 s)
Control Plane FederatedTwinAgent orchestrates: MC oracle → optimizer → HITL gate → knob push. What should change. Triggered by user; runs one GS iteration at a time
Management Plane /health endpoint, watchdog, session audit log. Is the system healthy. Always-on; independent of calibration state

The 60 / 15 / 12 Split

SetCountSourceRole
All simulator params60DPM (Design Parameter Manifest)Full input space
Dynamic bridge params15AP SSH poll at tnReal AP state populates simulator
Optimizer search knobs12Subset of the 15Parameters the optimizer can propose changing
Static DPM params45User-supplied DPMSite geometry, client types, apps — fixed during a session
Critical distinction. The 15-param bridge and the 12 search knobs are overlapping but not identical. Every search knob is also a bridge param (the AP reports its current value). But 3 bridge params are read-only observables (noise floor, CRC error, station count) — the optimizer cannot propose changing them because they are RF outcomes, not configuration choices.

§3 — Algorithm 2: Monte Carlo Sensitivity Oracle

The MC oracle computes the local gradient of QoE with respect to each of the 12 optimizer knobs at the current operating point GS_n. It uses central-difference finite differences — not random sampling. The word "Monte Carlo" refers to the repeated simulation runs (one per knob × 2 directions = 24 total per iteration), not to random exploration of parameter space.

Why central difference, not forward difference? Central difference ((f(x+h) − f(x−h)) / 2h) achieves second-order accuracy with the same number of function evaluations as forward difference. The simulator is cheap (milliseconds), so 24 runs per iteration is acceptable.
ALGORITHM MC_Sensitivity_Oracle(GS_n, DPM_static): ── Constants ───────────────────────────────────────────────────────────── h ← 0.05 // perturbation factor = ±5% of current value K ← 12 // number of search knobs D ← len(active_QoE_dimensions) sensitivity ← zeros(K × D) // output matrix: ∂QoE_d / ∂θ_i FOR i IN range(K): knob_i ← GS_n.knobs[i] θ_current ← knob_i.value IF knob_i.type == "continuous": θ_plus ← clip(θ_current × (1 + h), knob_i.min, knob_i.max) θ_minus ← clip(θ_current × (1 - h), knob_i.min, knob_i.max) dθ ← θ_plus − θ_minus // actual denominator ELIF knob_i.type == "boolean": θ_plus ← 1 // feature ON θ_minus ← 0 // feature OFF dθ ← 1 ELIF knob_i.type == "integer": θ_plus ← clip(round(θ_current × (1 + h)), knob_i.min, knob_i.max) θ_minus ← clip(round(θ_current × (1 - h)), knob_i.min, knob_i.max) dθ ← max(1, θ_plus − θ_minus) // guard against 0 denominator GS_plus ← copy(GS_n) with knobs[i].value = θ_plus GS_minus ← copy(GS_n) with knobs[i].value = θ_minus QoE_plus ← SimulatorAgent.run(GS_plus, DPM_static) QoE_minus ← SimulatorAgent.run(GS_minus, DPM_static) FOR d IN range(D): sensitivity[i][d] ← (QoE_plus[d] − QoE_minus[d]) / dθ // Units: ΔQoE_d per unit Δθ_i RETURN sensitivity // shape: [12 × D]; written to gs_history.sensitivity_json
Hardware ceiling enforcement. The clip() calls above enforce AP3000 hardware limits defined in AP3000_HARDWARE_LIMITS (e.g. max chan_width=80 MHz on wifi1, max_clients=100, MCS tier 0–11). Perturbing beyond hardware limits produces meaningless sensitivity values. Clip before every simulator call.

§4 — Algorithm 3: Coordinate Ascent Optimizer

The optimizer takes the sensitivity matrix from Algorithm 2 and proposes GS_n+1: the next set of knob values that should move QoE closer to the user's target. It uses coordinate ascent — adjusting one knob at a time, prioritised by leverage — rather than simultaneous gradient descent on all 12 dimensions. This makes each proposed change auditable: one knob → one reason.

ALGORITHM Coordinate_Ascent_Optimizer(GS_n, sensitivity, QoE_target, QoE_actual_n, CONFIG): ── Constants ───────────────────────────────────────────────────────────── α ← 0.10 // step size (learning rate) — 10% of gap per iteration K_top ← 3 // max knobs changed per iteration (keep changes auditable) ε_bool ← 0.05 // threshold: flip boolean knob only if |sensitivity| > this ── Step 1: Compute per-dimension progress gap ──────────────────────────── gap[d] ← QoE_target[d] − QoE_actual_n[d] // signed: positive = below target gap_norm ← norm(gap) // for weight normalization IF gap_norm == 0: RETURN GS_n // already at target ── Step 2: Compute per-knob aggregate leverage score ───────────────────── FOR i IN range(K): // Weight each dimension by how far we are from its target w[d] ← |gap[d]| / gap_norm // larger gap → higher weight // Sign: does this knob move us TOWARD target on each dimension? aligned[i][d] ← sign(sensitivity[i][d]) == sign(gap[d]) score[i] ← Σ_d ( |sensitivity[i][d]| × w[d] × aligned[i][d] ) // Knobs that are both high-sensitivity AND moving toward all targets score highest ── Step 3: Rank knobs; take top K_top ─────────────────────────────────── priority ← argsort(score, descending=True)[:K_top] GS_n1 ← deepcopy(GS_n) changes ← [] ── Step 4: Compute proposed change per selected knob ───────────────────── FOR i IN priority: knob ← GS_n.knobs[i] IF knob.type == "continuous" OR knob.type == "integer": // Gradient step: move each knob proportional to α × gap / sensitivity // Weighted average across dimensions Δθ ← Σ_d( w[d] × α × gap[d] / sensitivity[i][d] ) where sensitivity[i][d] ≠ 0 new_val ← clip(knob.value + Δθ, knob.min, knob.max) IF knob.type == "integer": new_val ← round(new_val) ELIF knob.type == "boolean": // Flip only if aggregate sensitivity exceeds threshold net_sensitivity ← Σ_d( w[d] × sensitivity[i][d] × sign(gap[d]) ) IF |net_sensitivity| > ε_bool: new_val ← 1 IF net_sensitivity > 0 ELSE 0 ELSE: new_val ← knob.value // no change — sensitivity too small to justify a flip GS_n1.knobs[i].value ← new_val changes.append({knob: knob.name, from: knob.value, to: new_val, score: score[i], reason: top_dimension(sensitivity[i], w)}) GS_n1.changes ← changes // written to gs_history.changes_json for audit GS_n1.iteration ← n + 1 RETURN GS_n1

§5 — Algorithm 4: QoE Vector Computation

5a — QoE from Real AP Measurements (QoE_actual)

The 5D QoE vector is computed from raw AP SSH poll outputs. All dimensions are normalized to [0, 1] where 1 = best possible.

#DimensionFormulaAP Fields UsedNotes
d0 Throughput Σ(tx_throughput_mbps) / (station_count × MCS11_peak) tx_throughput_mbps, station_count MCS11_peak = 1201 Mbps (80MHz 2×2 802.11ax). Normalized 0–1.
d1 Reliability 1 − (crc_error_pct / 100) crc_error_pct 0% CRC → 1.0; 100% CRC → 0.0. CRC is the primary frame-loss signal.
d2 Latency proxy 1 / (1 + M_D_1(ρ)) where M_D_1(ρ) = ρ / (1−ρ) and ρ = total_cu_pct / 100 total_cu_pct M/D/1 queue model. ρ → 1 makes delay → ∞. Clamped: ρ = min(ρ, 0.95).
d3 Connection quality MCS_tier(avg_snr_db) / 11 avg_snr_db (from client_polls) SNR → MCS tier via 802.11ax lookup table (see §5c). Normalized 0–1.
d4 Capacity headroom 1 − (tx_cu_pct + rx_cu_pct) / 100 tx_cu_pct, rx_cu_pct Clamped to [0, 1]. Represents remaining airtime for burst traffic.
QoE_actual = [ d0, d1, d2, d3, d4 ] where each d ∈ [0.0, 1.0]
Configurable dimensions. Any subset of {d0..d4} may be active per session. Users prioritising video calls might weight d2 (latency) and d3 (SNR) highest. A bulk-transfer session weights d0 (throughput) only. Default = all five, equal weight.

5c — δ Definitions (Two Deltas — Never Conflate)

DeltaFormulaMeaningAction on alarm
δ_calibration_n |QoE_predicted_n − QoE_actual_n| per dimension Is the simulator model accurately describing this AP? If > 20%: PAUSE loop, investigate DPM static params
δ_progress_n |QoE_target − QoE_actual_n| per dimension Are we moving toward the user's QoE goal? If < 10% of target: declare CONVERGED
Invariant. A small δ_calibration does NOT imply a small δ_progress. If the model is accurate but the AP is far from target, the correct action is to change knobs — not to re-calibrate. These two paths must never be conflated in code.

§9 — Audit Trail (What Gets Written to DB)

Every GS iteration produces a complete audit record. The schema below is the regression test ground truth — any re-run with the same GS_0, DPM_static, and CONVERGENCE_CONFIG must reproduce the same GS_history records.

TableWritten whenKey fields
sessions Session open / close id, ap_ip, ap_name, ap_model, start_ts, end_ts, config_snapshot_json
radio_polls Every poll (POLL_INTERVAL) All 65 data fields + session_id, ts, radio, band
client_polls Every poll session_id, ts, radio, mac, snr_db, tx_rate_mbps, rx_rate_mbps, ...
knob_change_events Sprint 2b: user manual change via knob panel
Sprint 3+: optimizer-proposed GS push (HITL approved)		 session_id, ts, knob_name, old_value, new_value, source (user|optimizer), gs_iteration
gs_history (Sprint 3) End of each GS iteration session_id, iteration_n, gs_record_json, qoe_actual_json, qoe_predicted_json, delta_calibration_json, delta_progress_json, sensitivity_json, changes_json, verdict, ts_start, ts_end
raw_cli_snapshots Every poll (debug mode) session_id, ts, radio, tag, raw_text
Regression test invariant. Given identical inputs (gs_history[n].gs_record_json as GS_n, same DPM_static, same CONVERGENCE_CONFIG), Algorithm 2 must produce identical sensitivity_json, and Algorithm 3 must produce identical changes_json and GS_n+1. The simulator must be deterministic (no random seeds in its physics equations).
