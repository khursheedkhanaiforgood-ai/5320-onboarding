v1.2 APPROVED    Authored: 2026-06-09  ·  Revised: 2026-06-09  ·  AP Platform: AP3000 HiveOS (WiFi 6)  ·  Scope: Sprint 2b–Sprint 5  ·  Audit reference: docs/dt_algorithm_spec.html

Purpose. This document is the authoritative algorithm specification for the DigitalTwinEngine calibration loop. It serves three roles simultaneously: (1) audit record for any third-party review of the optimization methodology, (2) regression test oracle — every Sprint 3 unit test must produce outputs consistent with the equations here, and (3) implementation contract — Sprint 3 code is written against this spec, not the other way around.

§1 — System Overview

The DigitalTwinEngine operates three concurrent planes:

PlaneFunctionState Machine
Data Plane AP3000 → SSH → APCollectorAgent → SQLite + Dash. What is happening on the radio. Running continuously at POLL_INTERVAL (default 15 s)
Control Plane FederatedTwinAgent orchestrates: MC oracle → optimizer → HITL gate → knob push. What should change. Triggered by user; runs one GS iteration at a time
Management Plane /health endpoint, watchdog, session audit log. Is the system healthy. Always-on; independent of calibration state

The 60 / 15 / 12 Split

SetCountSourceRole
All simulator params60DPM (Design Parameter Manifest)Full input space
Dynamic bridge params15AP SSH poll at tnReal AP state populates simulator
Optimizer search knobs12Subset of the 15Parameters the optimizer can propose changing
Static DPM params45User-supplied DPMSite geometry, client types, apps — fixed during a session
Critical distinction. The 15-param bridge and the 12 search knobs are overlapping but not identical. Every search knob is also a bridge param (the AP reports its current value). But 3 bridge params are read-only observables (noise floor, CRC error, station count) — the optimizer cannot propose changing them because they are RF outcomes, not configuration choices.

Two Clocks — Invariant

The AP polling loop never stops. It runs on CLOCK 1 continuously at POLL_INTERVAL. The GS convergence loop runs on CLOCK 2 as discrete triggered events overlaid on top. This invariant must hold in all sprint implementations.

ClockFrequencyWhat it doesStops when
CLOCK 1 — Data plane Every POLL_INTERVAL (15 s) SSH poll → radio_polls row. Continuous RF ground truth. Only on clean session exit or AP disconnect.
CLOCK 2 — Control plane User-triggered; one GS iteration at a time MC oracle → optimizer → HITL gate → AP push → stabilization → QoE sample. On any convergence verdict.

QoE_actual_n is a Windowed Average

A single poll is noisy. QoE_actual_n is the mean over the last window_polls (default 5) radio_polls rows collected while GS_n was active, after the stabilization window has elapsed.

QoE_actual_n = mean{ compute_qoe(row) : row ∈ radio_polls
  WHERE session_id = S
  AND ts > (gs_push_ts_n + stabilization_polls × POLL_INTERVAL)
  AND ts < gs_push_ts_{n+1}
  ORDER BY ts DESC LIMIT window_polls }

Each radio_polls row carries a gs_label column (NULL before first GS push; 'GS_0', 'GS_1', … thereafter), populated by FederatedTwinAgent from the knob_change_events timestamp. This enables direct SQL queries such as:

-- Before/after comparison, no joins needed SELECT gs_label, AVG(crc_error_pct) AS avg_crc, AVG(total_cu_pct) AS avg_cu, AVG(link_score) AS avg_score, COUNT(*) AS polls FROM radio_polls WHERE session_id = ? GROUP BY gs_label ORDER BY gs_label;

§3 — Algorithm 2: Hessian Oracle (Gradient + Full Interaction Matrix)

The oracle computes both the gradient (first-order: how QoE changes per knob) and the Hessian (second-order: how knobs interact with each other). The Hessian off-diagonal entry H[i,j] ≠ 0 means knobs i and j are coupled — changing both together produces a different result than the sum of changing each alone. This is the mathematical capture of all pairwise dependencies.

All calls use central-difference finite differences — not random sampling. Total cost: 24 runs for the gradient + 264 runs for the off-diagonal Hessian = 288 simulator calls per iteration. At ~1 ms per call: ~0.3 seconds. Acceptable.

Why compute the full Hessian instead of just the gradient? Coordinate ascent (gradient only) changes one knob at a time and zigzags toward the optimum when knobs interact. Newton's method (gradient + Hessian) takes a joint step across all 12 knobs simultaneously, in the direction that accounts for all interactions. The Hessian IS the interaction matrix — its off-diagonal entries are the coupling strengths between knob pairs, and it is also what auditors and regulators can inspect to understand why a particular set of changes was recommended.
ALGORITHM Hessian_Oracle(GS_n, DPM_static): h ← 0.05 // perturbation factor ±5% K ← 12 // knobs D ← len(active_QoE_dimensions) gradient ← zeros(K × D) // ∂QoE_d / ∂θ_i (first order) hessian ← zeros(K × K × D) // ∂²QoE_d / ∂θ_i∂θ_j (second order) ── Part 1: Gradient — 24 simulator calls ──────────────────────────────── FOR i IN range(K): θ_plus_i, θ_minus_i, dθ_i ← perturb(GS_n.knobs[i], h) QoE_plus_i ← Simulator.run(copy(GS_n, knob_i=θ_plus_i), DPM_static) QoE_minus_i ← Simulator.run(copy(GS_n, knob_i=θ_minus_i), DPM_static) FOR d IN range(D): gradient[i][d] ← (QoE_plus_i[d] − QoE_minus_i[d]) / dθ_i ── Part 2: Off-diagonal Hessian — 66 pairs × 4 calls = 264 simulator calls FOR i IN range(K): FOR j IN range(i+1, K): // upper triangle only; H is symmetric θ_pi, θ_mi, dθ_i ← perturb(GS_n.knobs[i], h) θ_pj, θ_mj, dθ_j ← perturb(GS_n.knobs[j], h) // 4-point cross-difference: ∂²f/∂θᵢ∂θⱼ Q_pp ← Simulator.run(copy(GS_n, knob_i=θ_pi, knob_j=θ_pj), DPM_static) Q_pm ← Simulator.run(copy(GS_n, knob_i=θ_pi, knob_j=θ_mj), DPM_static) Q_mp ← Simulator.run(copy(GS_n, knob_i=θ_mi, knob_j=θ_pj), DPM_static) Q_mm ← Simulator.run(copy(GS_n, knob_i=θ_mi, knob_j=θ_mj), DPM_static) FOR d IN range(D): cross ← (Q_pp[d] − Q_pm[d] − Q_mp[d] + Q_mm[d]) / (dθ_i × dθ_j) hessian[i][j][d] ← cross hessian[j][i][d] ← cross // symmetric ── Diagonal Hessian terms (from gradient calls, no extra cost) ─────────── FOR i IN range(K): QoE_0 ← Simulator.run(GS_n, DPM_static) // cache — only once FOR d IN range(D): hessian[i][i][d] ← (QoE_plus_i[d] − 2×QoE_0[d] + QoE_minus_i[d]) / (dθ_i²) RETURN gradient, hessian // Both written to gs_history: gradient_json, hessian_json (auditable)

perturb() helper — handles all knob types

FUNCTION perturb(knob, h): IF knob.type == "continuous": θ+ ← clip(knob.value × (1+h), knob.min, knob.max) θ− ← clip(knob.value × (1-h), knob.min, knob.max) dθ ← θ+ − θ− ELIF knob.type == "boolean": θ+ ← 1; θ− ← 0; dθ ← 1 ELIF knob.type == "integer": θ+ ← clip(round(knob.value × (1+h)), knob.min, knob.max) θ− ← clip(round(knob.value × (1-h)), knob.min, knob.max) dθ ← max(1, θ+ − θ−) // guard: never divide by zero RETURN θ+, θ−, dθ
Hardware ceiling enforcement. All clip() calls enforce AP3000_HARDWARE_LIMITS: chan_width ≤ 80 MHz (wifi1), max_clients ≤ 100, MCS ≤ 11, no 6 GHz / wifi2 params. Perturbing beyond hardware limits produces physically meaningless Hessian entries.

§4 — Algorithm 3: Newton Optimizer with MINLP Structure

The optimizer uses the full Hessian from Algorithm 2 to take a joint Newton step across all 12 knobs simultaneously. This replaces coordinate ascent (which changes one knob at a time and fails when knobs interact). The Hessian inverse H⁻¹ rotates the gradient into the natural coordinate system of the QoE surface — the step automatically compensates for inter-knob coupling.

Because 5 of the 12 knobs are boolean, the problem is formally MINLP (Mixed Integer Nonlinear Programming). We exploit the small boolean count (2⁵ = 32 combinations) to handle the integer subspace exactly via enumeration, while applying Newton's method to the 7 continuous/integer knobs within each boolean configuration.

Sprint 3 vs Sprint 4 scope. Sprint 3 implements Stage A only (Newton on full 12D with projection for booleans) — sufficient for a lab AP with few clients. Sprint 4 adds Stage B (Branch & Bound over all 32 boolean configurations + Bayesian Optimization for the continuous sub-problem).
ALGORITHM Newton_MINLP_Optimizer(GS_n, gradient, hessian, QoE_target, QoE_actual_n, CONFIG): ── Inputs (from Algorithm 2) ───────────────────────────────────────────── // gradient[K][D], hessian[K][K][D] // (K=12 knobs, D=active QoE dimensions) ── Step 1: Weighted objective gradient (collapse D dimensions → 1 vector) ─ gap[d] ← QoE_target[d] − QoE_actual_n[d] // signed gap per dimension w[d] ← |gap[d]| / norm(gap) // dimension weights: bigger gap → more weight g[i] ← Σ_d ( gradient[i][d] × w[d] × sign(gap[d]) ) // weighted gradient, shape [K] H[i][j] ← Σ_d ( hessian[i][j][d] × w[d] ) // weighted Hessian, shape [K×K] ── Stage A (Sprint 3): Joint Newton step over all 12 knobs ─────────────── // Newton direction: Δθ = α × H⁻¹ × g // Use damped Newton (add λI to H for numerical stability if H is near-singular) λ ← 1e-4 H_reg ← H + λ × I // regularised Hessian Δθ ← CONFIG.step_size_alpha × solve(H_reg, g) // linear solve, not matrix inverse GS_n1 ← deepcopy(GS_n) changes ← [] FOR i IN range(K): knob ← GS_n.knobs[i] IF knob.type == "continuous": new_val ← clip(knob.value + Δθ[i], knob.min, knob.max) ELIF knob.type == "integer": new_val ← clip(round(knob.value + Δθ[i]), knob.min, knob.max) ELIF knob.type == "boolean": // Project: if Newton step pushes past 0.5 threshold, flip projected ← knob.value + Δθ[i] IF projected > 0.5 AND knob.value == 0: new_val ← 1 // flip ON ELIF projected < 0.5 AND knob.value == 1: new_val ← 0 // flip OFF ELSE: new_val ← knob.value // no flip IF new_val != knob.value: // Record reason: which QoE dimension drove this change, and Hessian coupling strength top_dim ← argmax_d(|gradient[i][d]| × w[d]) couplings ← {j: H[i][j] for j ≠ i if |H[i][j]| > 0.01} // significant cross-terms changes.append({knob: knob.name, from: knob.value, to: new_val, newton_step: Δθ[i], primary_dim: top_dim, coupled_knobs: couplings}) // AUDIT RECORD GS_n1.knobs[i].value ← new_val GS_n1.changes ← changes GS_n1.iteration ← n + 1 RETURN GS_n1 ── Stage B (Sprint 4): MINLP Branch & Bound over boolean subspace ───────── // 2^5 = 32 boolean configurations; optimize continuous knobs within each best_QoE ← −∞; best_GS ← None FOR b IN all_32_boolean_configs: IF INTERACTION_GRAPH.prune(b, QoE_actual_n): CONTINUE // prune: e.g. skip OFDMA=ON if chan_width=20MHz // skip MU-MIMO=ON if station_count < 2 // skip BSS-Color=ON if neighbor_count == 0 GS_b ← copy(GS_n) with boolean knobs set to b GS_b_opt ← Newton_continuous_subproblem(GS_b, DPM_static, CONFIG) QoE_b ← Simulator.run(GS_b_opt, DPM_static) QoE_scalar ← Σ_d( QoE_b[d] × w[d] ) IF QoE_scalar > best_QoE: best_QoE ← QoE_scalar best_GS ← GS_b_opt RETURN best_GS // global optimum over boolean subspace + local optimum in continuous

§5 — Algorithm 4: QoE Vector Computation

5a — QoE from Real AP Measurements (QoE_actual)

The 5D QoE vector is computed from raw AP SSH poll outputs. All dimensions are normalized to [0, 1] where 1 = best possible.

#DimensionFormulaAP Fields UsedNotes
d0 Throughput Σ(tx_throughput_mbps) / (station_count × MCS11_peak) tx_throughput_mbps, station_count MCS11_peak = 1201 Mbps (80MHz 2×2 802.11ax). Normalized 0–1.
d1 Reliability 1 − (crc_error_pct / 100) crc_error_pct 0% CRC → 1.0; 100% CRC → 0.0. CRC is the primary frame-loss signal.
d2 Latency proxy 1 / (1 + M_D_1(ρ)) where M_D_1(ρ) = ρ / (1−ρ) and ρ = total_cu_pct / 100 total_cu_pct M/D/1 queue model. ρ → 1 makes delay → ∞. Clamped: ρ = min(ρ, 0.95).

d4 Capacity headroom 1 − (tx_cu_pct + rx_cu_pct) / 100 tx_cu_pct, rx_cu_pct Clamped to [0, 1]. Represents remaining airtime for burst traffic.
QoE_actual = [ d0, d1, d2, d3, d4 ] where each d ∈ [0.0, 1.0]

5c — δ Definitions (Two Deltas — Never Conflate)

DeltaFormulaMeaningAction on alarm
δ_calibration_n |QoE_predicted_n − QoE_actual_n| per dimension Is the simulator model accurately describing this AP? If > 20%: PAUSE loop, investigate DPM static params

Invariant. A small δ_calibration does NOT imply a small δ_progress. If the model is accurate but the AP is far from target, the correct action is to change knobs — not to re-calibrate. These two paths must never be conflated in code.

§6 — Algorithm 5: Bayesian Optimization Pre-Search on Simulator (Sprint 4)

Before the first real AP push, run Bayesian Optimization on the simulator to find GS* — the globally optimal configuration in simulation space. This replaces the first gradient step with a properly explored starting recommendation. A Gaussian Process builds a probability distribution over the QoE surface; the acquisition function decides where to sample next.

ALGORITHM BO_Simulator_PreSearch(GS_0, DPM_static, QoE_target, CONFIG): // GP surrogate with mixed kernel: // Continuous/integer knobs → Matérn-5/2 kernel // Boolean knobs → Hamming distance kernel // Combined via product kernel GP ← GaussianProcess(kernel=MixedKernel(KNOB_SPEC)) X_obs ← [GS_0] Y_obs ← [scalar_QoE(Simulator.run(GS_0, DPM_static), QoE_target)] FOR iteration IN range(CONFIG.bo_budget): // default bo_budget = 200 simulator calls GP.fit(X_obs, Y_obs) // update surrogate with all observations // Expected Improvement acquisition: E[max(QoE(θ) − QoE_best, 0)] θ_next ← argmax_θ EI(θ, GP, QoE_best=max(Y_obs)) // θ_next is constrained to AP3000 hardware limits // Boolean dims use integer relaxation then round Y_next ← scalar_QoE(Simulator.run(θ_next, DPM_static), QoE_target) X_obs.append(θ_next); Y_obs.append(Y_next) GS_star ← X_obs[argmax(Y_obs)] // GP posterior at GS_star gives confidence interval: μ, σ ← GP.predict(GS_star) CI_95 ← (μ − 1.96×σ, μ + 1.96×σ) // presented to user at HITL gate RETURN GS_star, CI_95 // User sees: "Pushing these 12 knobs has 95% CI of improving QoE by [X, Y]"
What BO adds beyond Newton. Newton's method finds the nearest local optimum. BO explores the full simulator space and finds the global optimum (within the bo_budget). With 200 simulator calls (~0.2 seconds), BO can evaluate all 32 boolean combinations plus explore the continuous space thoroughly. The GP covariance matrix explicitly encodes which knob combinations are correlated — and the 95% confidence interval at HITL gives the user a statistically grounded reason to approve or reject the push.

Known pairwise dependencies from 802.11 physics. These are hard-coded into the INTERACTION_GRAPH.prune() function (Stage B, Algorithm 3) and displayed in the FederatedDashboard knob panel. When the Hessian confirms a coupling, it is annotated as physics-confirmed; when the Hessian H[i,j] is near-zero for a theoretically coupled pair, it is flagged as "inactive in current conditions."

K07 OFDMA-DLK04 Chan Width Synergistic Always coupled OFDMA subdivides the channel into Resource Units (RUs). 80 MHz → 37 RUs; 20 MHz → 9 RUs. Enabling OFDMA on 20 MHz gives near-zero multi-user gain. These knobs must move together.
K08 OFDMA-ULK04 Chan Width Synergistic Always coupled Same as OFDMA-DL — uplink trigger-frame scheduling requires sub-channel space.
K07 OFDMA-DLK08 OFDMA-UL Subadditive When both enabled Combined gain < sum of individual gains. Airtime shared between DL+UL scheduling. Enabling both provides diminishing marginal return on the second feature.

K09 MU-MIMOK07 OFDMA-DL Subadditive When both enabled Both are 802.11ax multi-user features competing for the same scheduler. Combined gain is typically 10–15% less than predicted by treating them as independent.

If the Hessian oracle returns H[K07][K04] ≈ 0 while OFDMA is enabled, it indicates the current operating point is already at the interaction boundary — not that the interaction is absent. Log both the theoretically expected coupling and the empirically measured H[i,j] in gs_history.hessian_json for audit.

§8 — Optimization Method Progression

The system upgrades its optimizer as more data accumulates. Each sprint adds a mathematically more powerful method while keeping the prior method available as a fallback.

MDP / Reinforcement Learning — Long-Term Architecture

Every GS iteration is a (state, action, reward) tuple:

state = QoE_actual_n (5D vector at time n)
action = Δknobs = GS_n+1 − GS_n (the proposed change)
reward = −δ_progress_n+1 (negative gap = higher reward when gap shrinks)

The gs_history table IS the RL replay buffer. After ~50 sessions across different conditions (low density, high density, interference present, interference absent), a Deep Q-Network trained on this buffer learns the optimal knob policy for this AP in its specific environment — capturing all interactions, including three-way and higher-order effects that the pairwise Hessian misses.

MCMC for uncertainty quantification (available alongside any optimizer). Markov Chain Monte Carlo sampling from the GP posterior gives calibrated confidence intervals on every recommendation — not just a point estimate but a full probability distribution over expected QoE. The HITL gate can display: "95% probability that enabling OFDMA-DL will improve throughput by [4.2, 18.7] Mbps given current station count and channel conditions." This is the statistical foundation for a defensible audit trail.

Regression test invariant. Given identical inputs (gs_history[n].gs_record_json as GS_n, same DPM_static, same CONVERGENCE_CONFIG), Algorithm 2 must produce identical sensitivity_json, and Algorithm 3 must produce identical changes_json and GS_n+1. The simulator must be deterministic (no random seeds in its physics equations).
